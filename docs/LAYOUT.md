# Unity venue conventions

How work files into any Unity venue this workspace touches. Three situation facts drive everything here: a venue is untracked but reproducible (packages from `vpm-manifest.json`, vendor content from the asset library, binaries from external backup); vendor content is licensed, not ours; the agent is the venue's primary editor. The named trees and path predicates below are properties of venues this workspace seeds — a foreign venue (a personal project reached over MCP) gets the principles, judged per-asset, not the trees, and path-keyed tool routing (`CheckAvatar`'s vendor routing, `OwnMaterial`'s dispositions) weakens there accordingly. The act of importing a vendor package is the `import-vendor-asset` skill; this doc owns where results land and why.

## Principles

- **Vendor content is untouched, reproducible, not kept.** `Assets/Vendor/` and `Packages/` are read-only to our tooling: a tool that would mutate an asset there materializes an owned copy first, and writability is judged per-asset, by path (an owned controller may reference a vendor clip — that clip stays read-only). Vendor content reproduces from the asset library — whose location is machine-local (`CLAUDE.local.md`) and never enters a tracked file — or from `vrc-get resolve`. Mutation under `Vendor/` is sanctioned only by §Vendor mutation's enumeration, and every sanctioned mutation carries its own replay recipe. This is policy on deliberate edits, not a byte contract: VPM restores and importer migrations rewrite these trees with no agent and no breach.
- **Provenance is a property of each reference, not of a folder.** Our work references vendor assets by GUID, never by path, so it survives a bare re-import; owning is selective — an owned asset tracks only what it actually changed and keeps GUID-referencing the vendor original for everything it didn't. Corollary: co-located naming (`Avatars/Chocolat` beside `Vendor/Avatars/Chocolat`) is a browsing convention, never dependency linkage.
- **Durability is diffability.** Durable work is what diffs cleanly — YAML (scenes/prefabs/materials), `.meta`, `.json`, scripts. Binaries (`.fbx` `.blend` `.psd` `.png`, audio) are never durable; each keeps its `.meta` beside it on disk, whose GUID and import settings are what let a re-exported file rebind without touching a single reference. Restoring a venue is the external backup's job, not the repo's (§The venue's git repo) — a restored venue has no meshes or textures until they are restored or re-exported. RunLog JSON is per-run diagnostics, disposable.
- **Durable work never references a disposable bucket.** `Agent/RunLogs/` and `Agent/Scratch/` are purged wholesale, on no notice and with no reference check — that is what *disposable* buys. Nothing durable — scene, prefab, controller, clip — may reference an asset inside one; a probe worth keeping graduates its assets out of the bucket *before* it becomes durable. The failure mode is why this is a rule: a purge leaves the durable asset silently unopenable, and afterwards every reference into the bucket reads identically absent — nothing on disk distinguishes a scene the purge broke from one never wired up. A top-level `Scratch/` is the same bucket wearing a different name; this doc grants no such folder, and anything found in one is disposable wherever it sits.
- **One logical asset, one home, filed by the axis held constant.** An owned asset's `Assets/` and `Blender/` homes are the same logical asset in two trees — load-bearing, not cosmetic: a fit gate resolves the `.blend` by mirroring the prefab's folder from `Assets/` into `Blender/` and taking the `.blend` whose stem equals the prefab's stem. A bucket holds one asset or a **family** — sibling assets holding the same axis constant, one prefab per sibling at the bucket top over shared `Models/`, `Materials/`, `Textures/`, `Animations/`, and one `.blend` per sibling in the mirrored bucket — and the stem rule reads both shapes without branching on which. Owned outfits file base-first (the base fitted to is held constant; a vendor package stays outfit-first, its bases varying inside it); one outfit fitted to two bases is two buckets, two `.blend`s — duplication accepted over cross-base sharing. History never forks a bucket: a refit files in the same owned shape as anything else, and baked-ness is a mesh stamp (`avatarprep_baked`), never a folder axis.
- **The tree is for browsing; truth is stamped on the asset.** Authoritative provenance is the `(base, state)` stamp in the mirrored `.blend` — stamp semantics and naming policy are `blender.md`'s — or, where a bucket has no mirror (a refit), its provenance sidecar. A stamp missing at filing or fit time means ask the operator, write the stamp back, and refile into the correct bucket; the `own-mergeable` skill owns that loop.
- **Our organizing layer stays shallow, legible, outside vendor structure.** Vendor content categorizes one level deep — `Vendor/<Category>/<Package>` — and we never nest our own structural decisions deeper inside `Vendor/`; a new vendor system gets a new category (`Vendor/FaceTracking/`), not a folder buried under an avatar. Folders we author use English names even when vendors ship Japanese ones. The one exception: **a vendor tool that resolves its own content by path** — scanning its install directory, or hard-coding `Assets/…` literals in its editor scripts — stays at that native path with its content-packages inside it, because relocating blinds the scan or nulls the loads. Grep a package's editor scripts for `"Assets/` before moving it and read every hit: a literal passed alongside a **GUID fallback** survives the move, a bare `LoadAssetAtPath` literal does not (MochiFitter is the scanning case; `docs/mochifitter.md` owns the mechanics).

## The venue's git repo

A venue is untracked by the workspace repo and carries **its own git repo**, whose only job is diff, log and blame over hand-authored text. Not backup, not recovery, not distribution — the external backup owns those, and that is why the tracked set can be as small as it is.

- **Allowlist, never denylist.** The venue `.gitignore` denies every file (`*`), lets git descend (`!*/`), denies the regenerated and vendor trees, then re-includes the hand-authored patterns — controller `src/*.yaml`, per-item `README*.md`, `Agent/Snapshots/*.md`, `Blender/` sidecars, `ProjectSettings/*.asset`, both `Packages/` manifests, the ignore files themselves. A denylist is an unwinnable race against Unity, where every new asset type is a silent hole. **Rule order is a correctness constraint**: `!*/` matches every directory and the last matching rule wins, so a directory deny placed before it is un-ignored and the re-includes then fire inside `Library/` and `Vendor/`. The file states the order and the check that proves it.
- **Every re-include is anchored to its real root.** An unanchored pattern reaches into any tree the denies only stop git from *descending* into, and `Packages/.gitignore` is regenerated by the package manager, so no root rule can outrank what it re-includes. Anchoring is what makes that harmless — confirm by test, never by reading the two files against each other.
- **Not tracked, and this is the decision, not an oversight:** prefabs, scenes, `.asset`, `.controller` and `.anim` (Unity reserialises them wholesale; a controller's authored intent is its `src/*.yaml`, from which the emit is deterministic and GUID-preserving), every `.meta` (GUID churn, in volume), and all binaries.
- **No remote, ever.** Venue content is private and this workspace is live public, so a remote is standing exposure against zero gain. Local-only also keeps the venue repo out of the account-routing surface entirely.
- **No hooks, no LFS, one branch, and never a worktree of a venue.** Agents commit deliberately at checkpoints with a one-line message. A venue worktree invites repointing a live Editor at it, which is the failure this avoids.
- **A venue's `.ignore` is what keeps the allowlist from blinding every search.** Under `*`, a `Grep` would otherwise see only the tracked set. The `.ignore` cancels that with `!**` and re-denies the heavy trees itself; it re-includes nothing, because under an allowlist there is nothing left for a file-level re-include to answer. `!**` also overrides ripgrep's skip-hidden rule, so `/.git/` is re-denied explicitly or every search reads git internals. Editing it is the operator's sign-off (`venue-ignore-audit`).
- **Venue prose sits outside the governed fence, deliberately.** The tracked READMEs and sidecars are agent-read prose, but the fence keys on not-ignored paths and every venue is ignored here, so `check_prose.py` never sees them. Write them to the same standard by hand.

## The trees

- **`Assets/Vendor/<Category>/<Package>`** — vendor imports as-dropped, plus `Vendor/_Common/<Seller>_<What>` for a folder a seller ships separately across its own packages, one bucket per seller. **Seller is the only key, and consumer count relocates nothing** — a second consumer appearing, or all but one falling away, moves no vendor content: the seller is what the import door already knows and it does not change, while a consumer-keyed bucket would churn live GUID references every time that set shifted, over a linkage folders never carried (§Principles, provenance is a property of each reference). A package's own `Common/` folder is package-local and stays inside it. `_Common/` takes shared *content* buckets only — a self-contained vendor system files as a `<Category>/<Package>` like any other. The scanning-tool exception above outranks all of it: a shared folder inside such a tool's install directory stays there. Everything else under `Assets/` is our work, durable, with no `Work/` wrapper.
- **`Assets/Avatars/<Name>/`** — the top level holds full prefabs only, one per asset (a family bucket holds several); owned controllers, clips, and params file in subfolders (the on-disk half of *owned = wired*, `animator.md`). **A family's shared menu-category assets file here too, in `Menu/`** (`Avatars/<Family>/Menu/Clothing.asset`): the category belongs to the base parent, while the leaves inside it are installed by whatever mergeable owns each piece (`menus.md`), so the asset is referenced from prefabs in three trees and must sit in the one bucket every wearer of the family already depends on. **An owned base is the triad** — prefab and exported FBX here, `.blend` in the `Blender/` mirror — and that, not the folder it sits in, is the discriminator: a base missing a leg is not owned yet, so work requiring one (a reproportion) routes to `own-base`.
- **`Assets/Outfits/<Base>/<Outfit>/`** — owned and refit outfits, base-first, the bucket keyed by the outfit or by a family of them; exported FBX under `Models/`, shared across a family's siblings. The outfit prefab carries the menu leaves for its own pieces, installed into the base family's category asset (`menus.md`), so nothing about an outfit's controls lives outside this bucket. A refit bucket carries `refit-provenance.json` beside the prefab (schema: the `mochifit` skill) instead of a `.blend` mirror — fully owning it later authors the bucket's reserved `.blend` in place (`own-mergeable`), keeping the sidecar for lineage, never a refile. A later-purchased official variant of the same outfit imports beside it under `Vendor/`, never colliding with it.
- **`Assets/Configurations/<Family>/`** — configuration prefabs: one prefab **variant** per complete wearable combination, owning its own avatar record and only the menu leaves no single mergeable can own — a reaction reaching from one composed mergeable into another, a leaf that exists on only one form of the body (`menus.md`) — filing beside `Avatars/` rather than inside it because it composes mergeables it does not own. It keeps a family bucket's top level to the form prefabs configurations derive from, and this tree has **no `Blender/` mirror** — a configuration owns no geometry, so the stem-matched `.blend` lookup never reaches here.
- **`Assets/Materials/<Avatars|Outfits>/<Name>/`** — owned materials and their exported textures, base-independent like the art, mirroring `Photoshop/` by name — except when the geometry is also owned, materials file with it (one asset, one home). Copy semantics: the `own-material` skill.
- **`Blender/Avatars/`, `Blender/Outfits/`** — `.blend` sources at the venue root, outside `Assets/` (editing there never triggers a refresh), one bucket per `Assets/` bucket and one `.blend` per prefab, named by its stem: `Assets/Outfits/<Base>/<Outfit>/<Outfit>.prefab` ↔ `Blender/Outfits/<Base>/<Outfit>/<Outfit>.blend`, a family's `Assets/Avatars/<Family>/<Name>.prefab` ↔ `Blender/Avatars/<Family>/<Name>.blend`. A **workshop `.blend`** — one in the bucket with no prefab of its stem — is a working file, not an asset, and is never a lookup target. Proportion-edge JSONs co-locate with the avatar they target — an outfit carries no edge of its own — and are durable recovery artifacts; edge naming and stamping are `blender.md`'s. `vrc-blender-tools/edges/` is a sample library, never the source of a real apply.
- **`Photoshop/<Avatars|Outfits>/<Name>/`** — `.psd` source art, outfit-first (art is base-independent). PSDs are our work, never `Vendor/`; what enters Unity is a flattened PNG export into the owned-materials bucket (the `own-material` skill owns the contract and its defect cases).

## Vendor mutation: the sanctioned exceptions

"Untouched `Vendor/`" is the default, not an invariant — these are the enumerated cases where content under `Vendor/` legitimately changes, each marked by its own recovery artifact:

- **A vendor's own patcher never patches the base in place** — in-place destroys the original, and a later base re-import silently reverts it with nothing recording a patch ran. Reconstruct the parallel-patched layout a careful vendor would ship: patch a *copy* of the base FBX as a package sibling, write a provenance sidecar recording the replay recipe, repoint the DLC's variant prefab to the copy. Those three edits are the whole sanction; the procedure and the reproduction rule live in the `import-vendor-asset` skill's §Patch.
- **A blocking platform importer setting is ours to correct in place** — `.meta`-only, at the import door, through `ConformImportSettings` as the only sanctioned writer (no `force`: its whole scope is this class). Which settings, and why the sanction holds: `unity-tools.md`.
- **A self-writing vendor system's generated output is its own layout, not a breach** — VRCLens writes per-avatar assets under its own `User/<avatar>/`, non-redirectable by design. Its collateral is not covered: diff the vendor tree after any vendor-system apply (`unity.md` §Sharp edges carries the trap).
- **Benign in-place drift is not tampering** — lilToon rewrites a vendor `.mat` at import (version bump + new default props) with no agent acting. A vendor-integrity check protects intent, not bytes.
