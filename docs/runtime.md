# VRChat runtime ground truth

How the VRChat client actually runs an avatar: the animator, network, contact, physbone, and constraint behaviors that gimmick design lives or dies on. Established empirically — treat it as physics. Where a measurement's reach is bounded — emulator-only, in-game-unverified, an unpinned threshold — the line says so; absent that, take it as measured. The companion design doc is `gimmicks.md`.

**The 90% rule.** Empirically-tuned constants in working systems (delays, pulses, thresholds) are load-bearing — preserve them verbatim; change one only with a test (now an emulator run, `emulator.md`), not a hunch.

## Animator evaluation

- A layer takes **at most one transition per frame**. N-state chains (bit walks, dispatch hops) cost N frames minimum; budget accordingly.
- **Layer weight 0 still evaluates the state machine** — transitions fire and StateMachineBehaviours (parameter drivers) run; only the motion output is muted. Driver-only layers at weight 0 are a standard idiom.
- **Preserve the first three layers, and their order, in the avatar's own base FX.** Some VRChat worlds toggle base-FX layers 0/1/2 to override facial expressions, so those slots are load-bearing by *index* — an empty one is often reserved, **not** dead, and dropping or reordering any of the first three can break the override. Base-FX only: a merged animator (MA / VRCFury) can't know its landed index (it appends lower in the stack), so the convention never constrains it.
- Entry transitions evaluate **in list order, first match wins**. An entry ladder is a priority encoder — and a mis-ordered one silently shadows later entries (a real bug class; lintable).
- A state's `motion time` can be bound to a parameter: an analog input scrubs a pose clip's playhead with no blend tree. A state's `speed` can be parameter-bound too — including from outside over OSC, making timer durations externally tunable.
- Bool parameters can be compared with Greater/Less as floats (0/1); thresholds like >0.008 /
  <0.992 give edge-detection with hysteresis on nominally boolean signals.
- **Parameter type is per-reader, not global.** Unity animators are float-backed and VRChat casts on read, so a param's *synced expression* type is independent of how each animator reads it — declare a param that only needs discrete values as a 1-bit **bool** (or int) even though the FX animator consumes it as a **float** DBT weight/radial: the standard way to fold toggles into one Direct blend tree without paying 8 synced bits each. The merged-controller case (int in one, float in another → one VRC param) is the same mechanism; ints band-select via float Greater/Less compares (e.g. `10 ≤ Mode ≤ 19`).
- Write Defaults: keep it consistent per layer; direct-blend-tree layers want **WD ON** (the one sanctioned mix) — a Direct tree that reads back an AAP it also writes diverges without bound at WD OFF. On a **scene binding** (component field, transform channel, GO active) a state writes only what its own clip writes at either setting, within a layer and across them (measured in play), so a full-face override clip must key *every* shape it needs to own — WD ON restores nothing for you. Animator parameters are the exception, below.
- Transition `interruption` defaults to None; `canTransitionToSelf` on AnyState transitions re-fires the state every frame the condition holds — usually you want it off.
- **A parameter bound by any clip in the controller is owned by the animation system: nothing outside it can write that parameter.** Not a Parameter Driver, not an expression-menu control, not a contact, not `SetFloat`/`SetBool`. It holds at writeDefaults on *and* off, at layer weight 0 and 1, before the binding clip has ever played and after it releases — the conditions are listed because writeDefaults is the explanation to expect and is not the one. Such a parameter holds exactly two things: its declared default, and whatever a clip writes it. `RuleDriverOnAnimatedParam` refuses the driver case at compile.
- **Parameter curves write only `float` parameters.** A curve on a `bool` or `int` is emitted, sets nothing, and still binds the parameter — worse than absent, and the reason a "bool AAP" silently never works. An **AAP** is therefore always a float; `RuleNonFloatParamCurve` refuses the rest.
- **Inside the animator every reader sees an AAP's animated value; only outside writers are locked out.** A blend tree reads it, and so does a **transition condition**, one frame behind the clip's write (same for a same-layer and a cross-layer read) — so a clip-computed value can gate a state change. A driver `copy` source is the exception: it reads the parameter's **declared default**, which need not be zero. A driver *write* reaches no animator reader at all, though it still lands in the expression parameter — so a synced, OSC-out or `saved:` consumer sees it while every clip, tree and transition in the controller does not.
- **An AAP holds its last clip-written value whenever the active state's clip does not write it — except under a WD-ON *empty* state (`motion: ~`), which reverts it to its declared default** (measured in play; an edit-mode `Animator` disagrees on the clip-bearing case — `emulator.md` §Pure controller math). That exception is the failure mode of a persistence cell: park a memory AAP's layer in an empty state at WD ON and its value is gone each frame. An AAP crosses the wire only through an encoded proxy (`gimmicks.md`).

## Parameters and network sync

- Synced expression parameters: bool = 1 bit, int/float = 8 bits, 256-bit budget; synced ints are unsigned 0–255. **A float is native 32-bit locally; only its synced copy is 8-bit fixed-point [-1,1]** (255 steps ≈ 1/127; −1/0/+1 exact) — drivers/OSC can hold out-of-range or fine-precision values locally that remotes never see, so anything remote-visible must survive the quantized [-1,1]. The same locality holds for Ints, **defaults included**: an unsynced Int expression parameter carries values above 255 end to end — a code-authored default of 1000 serializes, initializes the runtime parameter, and reads back over OSC/OSCQuery unclamped (measured in-client) — every 0–255 clamp in the chain gates on `synced`. One trap rides this: the SDK's expression-parameters inspector *displays* every default clamped (Int 0–255, Float [-1,1]) without writing back, but a single keystroke in that row silently persists the truncation — a >255 default survives code and inspection, not a hand edit. PC↔mobile params match by **list position + type, not name** (why the VRCFury mobile build aligns param order, below). Sync is batched on a ~12 Hz tick. All params changed within a tick replicate together as one **coherent snapshot** — a step index and its data land atomically, so a multiplexing protocol needn't guard against a torn step+data read. The constraint is rate, not loss: a param changed twice inside one tick loses the intermediate, and a protocol that drops a snapshot pays a full cycle to re-send — so hold each step stable across several ticks and latch a coherent set. **A set→clear pair on a synced param needs ~0.2 s of separation to be seen remotely.** The floor binds the *pair*, not the state: a driver that sets a value and leaves it set is safe at any state duration, because the value persists and occupancy time never enters — so a lint predicated on state duration would fire across a clean corpus. One tick is only the *phase* bound: a value held a full tick period is sampled whatever the phase, shorter holds probabilistically (emulator-measured). In-game the wire drops nothing measurable, so the 0.2 s floor is not tick count — it absorbs the frame clock, which is what actually degrades under load (`vrc-patterns/word-channel`).
- **The synced-param count is only knowable post-build.** The pre-build `VRCExpressionParameters` asset under-counts — Modular Avatar params, VRCFury synced toggles, and merged prefabs all inject synced params at build. To read the real count, enter play mode and check the populated descriptor; for the compressor's effect on it, read the `VRCFuryDebugInfo` "Parameter Compressor" component (§VRCFury build-time reshaping). Neither the pre-build asset nor the baked `networkSynced` flag is authoritative on its own.
- Synced params **late-sync**: late joiners receive current values. Everything else (animator-local params, contact/physbone outputs) is regenerated per-client.
- **IK body motion is smoothed/delayed (~0.5 s); physbone grab/pose sync is not.** Physbone events run ahead of the visible remote body. Consequences: remote drop positions need ~1 s of stillness to agree across clients; OSC apps compensating for this need activation/release delays.
- Parameter drivers: `localOnly=1` runs only on the wearer's client; `localOnly=0` also runs on every remote copy's animator — a driver can force a network-visible effect (e.g. clearing a physbone grab param on all clients). Driver writes **clip a synced Int to 0–255**, Set and Add alike; an **unsynced** Int on neither (measured in-client, reproduced in av3emu — `emulator.md` §Remote clone). So a driver-fed counter runs unbounded only while it stays unsynced.
- A driver **Copy with `convertRange`** clamps a source outside the declared range to the nearest bound (9999 through 0..2550 → 0..255 reads 255) and **truncates rather than rounds when the destination is an Int** (130 through 0..255 → 0..100 is 50.98 and lands 50). **The venues split only where the exact result is a whole number** — 205 through 0..255 → 255..0 is exactly 50 and av3emu lands 49 — so never calibrate a remap on an integer-boundary fixture. A protocol pairing two such copies for round-trip inversion should use complementary counters rather than trust the remap to invert exactly.
- **Mirror/camera clones replay the wearer's parameter values but do not execute StateMachineBehaviours, and traverse the state machine fresh from Entry.** This asymmetry is exploitable as a mirror-clone detector (drive a flag on the real avatar; the clone spawns with it pre-set and routes differently), yielding local-real / remote / mirror-clone discrimination. The emulator reproduces it — its MirrorReflection clone replays the local runtime's parameter lists every frame and runs no drivers — so the routing asymmetry is **emulator-verifiable** by the state each animator occupies, never by a param diff (`emulator.md`). Where the split needed is only **local+mirror vs remote**, an **unsynced parameter is already the discriminator**, free: a remote reads its default forever while a mirror replays the wearer's (measured). `IsLocal` does not substitute — it reads **true** on a mirror clone (`vrc-patterns/mirror-detect` routes on that).
- **A culled avatar stops running its animator.** VRChat culls what you can't see — off-camera view culling, distance-hide, max-avatars-shown, manual/perf hide — and a culled animator simply doesn't run. So make animators **deterministic**: resolve to the correct state from current parameter values alone (not from history or in-flight transitions), and they self-correct on resume. A **mirror view keeps a remote's copy running** — an avatar a client sees only as a reflection keeps evaluating. Bounds-inflation ("anti-cull") defeats view culling and closes both gaps below.
- **Culling pauses the animator; it does not reload it — and `IsAnimatorEnabled` is anti-correlated with the rebuild** (measured across all three mechanisms on one instrumented avatar):

  | | view cull | distance-hide | manual hide/show |
  |---|---|---|---|
  | `IsAnimatorEnabled` fired | no | **yes** | no |
  | animator rebuilt (state reset) | no | **no** | **yes** |

  **Where the flag fires, it fires one frame early — VRChat's documented contract, not a measurement of ours**: *"Returns `false` one frame before the avatar's animator is disabled, and `true` when it's enabled"* (https://creators.vrchat.com/avatars/animator-parameters/). That single pre-halt frame is the only observable `false` window, so a **resume is not detectable** and a rig that must react to a cull pre-arms on that frame — transitioning into the state it wants to resume into — rather than trying to notice the resume afterwards.

  Only manual hide/show rebuilds; distance-hide disables the animator and resumes it carrying prior state, neither unloading nor clean-reloading. So a red latch is not evidence of a reset, nor a white latch of continuity — don't lean on it in either direction. During the pause the copy's **synced params keep taking wire updates** while every entry driver of the skipped interval goes unfired, so a resume evaluates from *current* values with no memory of the gap (emulator-measured; the in-game delivery timing is unverified, so a receiver must be correct whether resume sees latest values or stale-then-next-tick) — and a finite step counter cannot distinguish that resume from continuous progress beyond its own period (`vrc-patterns/word-channel` measures the residual and its knobs).
- **A transient fired while a remote has you culled never reaches them.** Durable values are fine — a synced mode int survives a cull and re-derives on resume — but a momentary pulse rises and falls while that client's animator is not evaluating, so nothing there samples it. The same pause halts latch-and-chase re-derivation: a contact-tracked marker diverges the moment the observer looks away, promptly rather than gradually.
- On avatar change, VRChat does not zero the previous avatar's OSC-visible parameters — external apps must reset state on `/avatar/change`.
- OSC: `/avatar/parameters/<name>`; ports default 9000/9001 but are **discovered via OSCQuery** — never hardcode them (vrc-bridge discovers). Params need not be synced to be OSC addressable — but the *name* must survive the build (VRCFury build-time reshaping, below). OSC-driven floats sync to remotes only if declared synced; otherwise encode them (see `gimmicks.md` float→bool patterns).

## Contacts

- Receiver modes: Constant (0/1 while overlapping), OnEnter (one-frame pulse; honors `minVelocity`, tested once at entry), Proximity (0..1; `minVelocity` inert). Proximity is **receiver-scoped**, not sender-centered — the value rises as the sender's *nearest surface* reaches the receiver, so enlarging the *receiver* lengthens the falloff. The exact model (emulator-confirmed, measured to three decimals): `1 − clamp(dist / radius)` where `dist` runs from the sender's nearest point to the nearest point on the receiver's **axis segment** — a capsule is a swept sphere (segment length = height − 2·radius, world-scaled; **radius alone** sets the falloff length everywhere along the axis; uniform scale preserves the shape, it never becomes a sphere unless height ≤ 2·radius), a sphere is the same formula against the center, and capsule-vs-capsule resolves segment-to-segment with the sender's surface offset by min(gap, sender radius). A box
  receiver's center mode is **Chebyshev per-axis** — `max(|d| / halfExtent)` in box space, not
  spherical — and face mode is a pure linear unlerp along local −Z from the +Z face plane, so box falloff is axis-separable by construction (what a diameter-compensated multi-box cage wants). The strongest overlapping sender wins (values are not additive).
- **`allowSelf`/`allowOthers` filters are evaluated only at contact acquisition, never re-checked on latched contacts.** Animating filters shut after acquisition locks the receiver onto the sender(s) it already holds — the core of contact-tracker targeting. Corollaries: waiting-state receiver size controls how many senders latch at trigger (several in the zone = all latched); filter *changes* affect only future acquisitions (an animated `allowSelf` opt-in works); a latched contact that fully breaks (sender exits range) **cannot re-latch while filters are shut** — re-entry is a new acquisition, so a multi-receiver rig degrades to partial probe sets whose skewed equilibria look like tracking error. A latched contact also survives its filter flipping shut mid-overlap — the held value is the latch working (emulator-reproduced), not a bug.
- **A stowed contact receiver reads its parameter back as exactly 0** — its own GameObject deactivated, an ancestor deactivated, or the component disabled, with no difference between the three (measured in-client and in av3emu). The last real reading survives only in the non-public `restoreParamValue`, so nothing an animator or OSC consumer reads tells a stowed receiver from one whose sender left; a **slow** re-enable re-acquires, measured 2–4 frames in-client with the sender already in the volume (median 2.4 at 60 fps, unchanged by wearer locomotion) — budget the gap in frames, not milliseconds, since the frame clock is what degrades under load. Physbones and raycasts are unmeasured. Any machine that gates on sensing params across a disable must clear them itself (`gimmicks.md` off-state hygiene owns the idiom).
- **A Proximity receiver switched off and back on with no collision-scene step in between, its sender still in its volume, comes back deaf** — `IsColliding()` reads **true**, `paramValue` reads **exactly 0**, `restoreParamValue` still carries the last real reading — and stays deaf until a *slow* off→on cycle or until the sender leaves its volume and re-enters (both heal it every time, measured; a Constant receiver bounced the same way comes back reading correctly, so the trap is Proximity's alone). The unit is the scene's step, not the animator's frame: **the collision scene steps at most 60 times a second** — a moving sender's readout refreshed every 5th frame at 4 ms frames, every 2nd at 11 ms, every frame at 20 ms — and a receiver's enable and disable are applied only at a step, so an OFF the scene never stepped through never happened to it, while the receiver's own stow-to-zero did. At or below 60 fps every frame steps and a one-frame OFF re-acquires; above it, frames are skipped and a one-frame OFF lands entirely inside a skipped one with probability `1 − 60/fps` (measured: an OFF shorter than a step went deaf 16/28, one spanning a full step 0/27; a same-frame script bounce is the limit case and is deaf every time). So **an animator gating a receiver's GameObject must hold the OFF for at least `fps/60` frames, rounded up** — two frames covers 120 fps, three covers 180 — and one evaluation is never enough above 60 fps; at exactly 60, frame-time jitter can drop a step too (inferred from the cap, unmeasured — budget as if above). Re-acquisition after the ON is one step for Constant and two for Proximity (the 2–4 frames of the stow bullet at 60 fps). The failure is silent: the params read a clean zero, indistinguishable from nothing in range (`vrc-patterns/object-sync` carries the worked case). Step cadence, the deaf-iff-no-step rule, the Proximity-only scope and both remedies are emulator-measured under `Time.captureDeltaTime` standing in for frame rate; the deafness and its fingerprint were measured in-client.
- **Contact shape and plumbing fields do not animate.** `radius`/`height`/`size`/`position`/ `rotation`/`shapeType`/`localOnly`/`collisionTags`/`useFaceProximity`/`parameter` carry `[NotKeyable]` (attribute read via reflection; curve-drop behaviorally confirmed for `size` and `radius`) — clip curves on them are silently dropped (`allowSelf`/`allowOthers`/ `receiverType`/`minVelocity` do bind). Script writes to shape fields don't reach the sim either — not even across a GO enable-bounce — until `UpdateShape()`, and **`InitShape(true)` is not that door**: on an already-registered contact it mints a *fresh, unregistered* shape (`shape.id` → NullId), silently dropping the contact out of the sim where no later `UpdateShape()` recovers it. The animatable size knob is the host GO's **transform scale**: honored per-frame and **per-axis** (a non-uniform scale reshapes a box exactly, true-matrix through 90°-rotated parents; non-90° rotations under non-uniform scale shear — untested, avoid). `boxSizeAbsolute` ignores transform scale — probe the sim, never read it as ground truth. Runtime `collisionTags` edits never re-register with the manager — spawn a fresh sender instead of retagging one (all emulator-measured).
- Contacts are simulated on **every** client from replicated bone positions, but IK delay and per-client discrepancy mean remote-side triggers misalign — do not treat contact outputs as synced. Default: sense with `localOnly` receivers and sync a bool. When trigger latency matters, keep remote-firing receivers as the fast path *and* back them with a synced bool to catch missed triggers.
- Built-in senders on every avatar: `Head`, `Hand` (L/R), `Finger*`, `Torso`, `Foot` — remote players' bodies are queryable without them wearing anything. Auto head/hand contact placement varies per avatar (height/offset) — acquisition shapes should be generous (tall capsules) and identically placed if multiple receivers must latch the same target.
- The clamp is a hard floor: a receiver reads **exactly 0 at and beyond its range edge** (and when nothing overlaps) — the Custom-Object-Sync "contact bug" (`references/`) is this floor, not a defect. Keep the working volume off the boundary or bias the zero point.
- `localOnly=1` means the contact component **does not exist on remote clones**. Default to it: cheaper, and polite — because the bug below sums contacts *across* nearby players, local-only receivers stay off everyone else's solve. Per-shape limits (editor-enforced): size ≤ 6 units, radius ≤ 3, and 16 tags. **~24 receivers clustered in one spot, summed across nearby players, makes them read wrong values** — a known, VRChat-tracked bug with no workaround; keep clusters small.
- Two receivers writing the **same** param: while both are live **each writes it every frame**, and the frame's **last** write — what any animator reader sees — is the **last-enabled** one's (values aren't summed). It is enable order specifically: exchanging the senders so the other receiver reads high leaves the winner unmoved, so neither magnitude nor component order decides it and the strongest-sender rule above does not generalize from one receiver to two. Two riders. An **OSC consumer sees the parameter alternate** between both readings for the length of the overlap — the client puts both writes on the wire even though the animator's end-of-frame value never wavers — so an out-of-process reader needs the overlap closed, not merely the animator satisfied. And **av3emu does not reproduce the arbitration**, handing it to a fixed receiver that ignores enable order and the readings alike (`emulator.md`), so a multiplexing rig passes there for a reason that is not the client's. Stowing each receiver before enabling the next sidesteps the rule entirely — one live writer — at the re-acquisition cost the stow bullet above measures.
- **A proximity reading is temporally noisy in the client and bit-constant in the emulator, and the noise is coupled to the wearer's distance from the world origin rather than to how much the wearer moves.** The mechanism is float32 quantisation of the world coordinate, re-rolled every frame by any motion at all: at palm scale a desktop avatar's idle animation re-rolls it as thoroughly as running does, so a receiver rigid to its sender reads the same jitter at rest and under locomotion, and gross movement enters only by changing where the avatar is. Budget about one float32 ulp of the distance from origin per frame out to roughly a kilometre — measured peak-to-peak on a 0.3 m palm-scale readout: 0.001 mm at spawn, 0.01 mm at 100 m, 0.4 mm at 1000 m, and white there — then expect the law to go superlinear and stop being white, unbracketed between 1 km and 10 km, where the same readout is ~110 mm peak-to-peak and a slowly wandering bias. Any threshold or quantizer on a contact reading will **dither** near a boundary at range — the remedy is per failure mode, not a menu: a bare threshold needs hysteresis; a multi-limb quantizer needs redundant encoding *and* coherent (atomic) application — atomicity alone only prevents tearing, it does nothing about the dither itself. `vrc-patterns/object-sync` carries the worked measurement and the design that absorbs it, plus the case those numbers do not cover: a wearer-mounted cage reading a world-parked sender adds genuine relative motion on top of the quantisation and swings a full quantiser cell at 1000 m under desktop movement. The emulator is structurally blind to the whole class: a threshold rig proven rock-stable there can still dither in-client, so temporal-stability claims about contact readings are client-tier only (`verify.md`).

## PhysBones

- Grab and pose state are **natively networked** — the free transport for continuous spatial input. Two distinct things sync: a **live grab** transports only the grabber's world target point plus an `_IsGrabbed` flag — every client re-runs the solve locally, so the chain regenerates per client and remote fidelity is bounded by the grabber's IK-delayed hand. **An in-progress grab does not reach a late joiner.** Nothing about it is a synced value a joiner can pick up mid-flight, so its `_IsGrabbed` and chain pose read as never-grabbed — home, ungrabbed — until the next grab it is itself present for. Any grab-carried state a joiner must read correctly (a placed-vs-held distinction, a carry mode) needs its own synced representation, and that representation's *off* value must mean the reading a joiner actually gets: a prop flagged neither placed nor grabbed **is** home. The no-bit alternative resolves the same ambiguity by hiding the prop until a grab is witnessed (`vrc-patterns/grab-prop` §Late join). A **pose** (grab released with posing allowed) instead snapshots each bone's rotation **relative to its parent/root** — this **late-syncs in-game** (a late joiner sees the posed chain; the emulator does **not** reproduce it — a bone posed locally holds on the wearer but does not transport to a non-local clone) — which places nothing absolutely unless the root is already agreed, but is exactly right for fixed-frame inputs (control panels, slider/slide-rule interfaces). A "drop" implemented by moving or freezing an **underlying transform** (e.g. constraint toggling under the bone) is outside physbone sync entirely and does **not** late-sync: anyone loading the avatar afterward sees the original position until the next grab. `<param>_IsGrabbed`, `_Angle`, `_Stretch`, `_Squish` regenerate per-client from the synced grab at zero expression bits; declaring a natively-driven param (physbone outputs, behavior-driven) as synced is a no-op that only wastes bits — the local component re-drives it every frame, so the synced value never survives to be read (and remotes regenerate their own from the grab regardless).
- The solver runs on a fixed **60 Hz virtual step** (substepped), so physbone behavior is framerate-independent until a slow frame hits the substep cap. Grab feeds the hand as the solver's tip target and blends toward the solved pose by the chain's grab-movement weight; it does not rigidly pin the bone. Remote-grabbed objects still disagree slightly across clients (the IK-delayed hand) — exact placement needs a real position sync on top.
- **With `snapToHand 0` the client keeps the grab offset rigid in the grabbing hand** (measured in-game): the grabbed tip stays fixed in the palm while the wrist rotates, so the bone endpoint is a hand-frame point placed by wherever the hand closed on the prop, and the tip-to-hand vector is a per-grab constant a rotation readout can use. The SDK's editor grab helper applies that offset unrotated in world space, so the emulator gets this wrong for any grab-driven rotation rig — script the tip rigidly on the scripted hand rather than trusting the helper. With `snapToHand 1` the tip is the client's hand grab point, which sits well off the palm-capsule centre (in-game: about where a held ball would rest); its exact offset is unmeasured.
- Three independent 0..1 forces shape a chain, each scaled by its own falloff curve along the length: **pull** (positional restoring toward the rest/animated pose), **spring** (velocity/momentum carried across steps — high spring + low pull = floaty overshoot), and **stiffness** (*angular* restoring toward the bone's prior direction). "Springy" is spring; "snappy" is pull; they don't substitute for each other.
- Force-release requires **both** halves: disabling the physbone's component/GO breaks an in-progress grab network-wide, but a disabled physbone won't set its `_IsGrabbed` back to false — pair the toggle with a driver clearing the param.
- Even at pull=1 a chain keeps settling after grab/release — not a pull lag (at pull=1 the pull step adds none) but retained momentum via **spring** and angular **stiffness**; zero both for a near-instant snap. Systems that snapshot a physbone-descendant position on release still want a short delay first.
- `isAnimated` must be on for animated physbone properties to apply; `resetWhenDisabled` controls pose persistence across GO toggles. `immobile` is a **0..1 amount** (not a switch) with two modes: *All Motion* re-anchors against the full root transform (ignores both movement and rotation — a pure sensor), *World (Experimental)* cancels only world translation so avatar rotation still drives the chain.

## Constraints (VRC)

- VRC constraints resolve in dependency-ordered execution groups within one frame — a constraint whose target is a parent of, or whose source sits inside, another's target runs first, and each group's writes are visible to the next. So chains (A←B←C) are consistent per-frame and measurement through several hops is sound. Ordering is guaranteed only within one **avatar root**, not across avatars.
- Constraints solve **once per rendered frame** (not on the physics tick). A constraint's slot relative to the PhysBone solve is derived from the hierarchy relation between its **effective target transform** (TargetTransform-aware — the transform it drives, not the component's GameObject) and a physbone's **root** transform: target at or above the physbone root ⇒ **pre-physbone** (the constraint drives the chain); target or any source *inside* the chain ⇒ **post-physbone** (it reads the solved pose); dependence on IK/animation ⇒ post-local-avatar; no relation ⇒ post-physbone. So to steer a physbone-controlled transform the driven target must sit at or above that chain's root; to read one, source from inside it. **Trap:** a constraint that both drives and reads a physbone resolves to post-physbone — the drive side silently loses, so split steering and reading across two constraints. The full per-frame dynamics order is one pipeline — pre-physbone constraints → PhysBones → post-physbone constraints → Contacts → post-local-avatar constraints — so contact receivers sample **after** the physbone solve.
- `TargetTransform` lets a constraint component live on GameObject X while driving transform Y — the "affect that other object" indirection (the target is frozen at play start; edit-mode only, not animatable). Combined with GO active toggling this hosts editor-only alignment helpers and build-time-only behaviors.
- **Two world-anchor idioms with different guarantees:**
  - `FreezeToWorld=1` (source-less) — locks where the avatar *loads in on each client*; fixed but **not cross-client consistent**. Editor-friendly when enabled only at upload (avatar stays movable in scene; enabling it in-editor bloats bounds as avatars move).
  - Constraint source pointing at a transform inside a **never-instantiated prefab asset** ("World.prefab" trick) — resolves as world origin **for every client**; required under any absolute-position sync. **Survives remote cull cycles intact**: the origin displacement long attributed to this idiom belongs instead to the bit-multiplexed object-sync protocols riding on it, whose receive-side staging and multi-frame decode a pause interrupts (`vrc-patterns/word-channel` carries the measured splice model and the knobs that price it). The anchor is not the fragile part **at zero source offset** — a nonzero per-source offset on the pin is multiplied by each client's avatar scale factor (offset-frames bullet below), and past that it is the protocol on top that breaks, so hold a transform-sync design to §Animator evaluation's three pause/rebuild shapes rather than to this constraint. Position is only half the idiom: holding a subtree at world *scale* is §Scale's world-scale pin, and a world-unit rig usually needs both.
  - **Choose on what the frame's origin is *used for*, never on what rides it.** An origin that is **consumed** — read against by a reconstruction, a measurement, or any absolute-synced value — needs cross-client agreement, so only the prefab-asset source serves. An origin that merely has to be **inertially static** — a damper's parent, anything absorbing parent motion where the origin cancels out — is served by either, and the choice is cost. "Is this a reconstruction?" gets it backwards: a damper's parent frame can sit *underneath* a reconstruction and still not care where its own origin is, because the damped node converges on a target already world-correct on every client. Reuse a pinned frame that already exists above the rig — that beats adding a freeze, which costs a second component, a capture edge to arm, and a build-time gate keeping the irreversible capture from firing while you author.
- `FreezeToWorld` captures the frozen pose on its 0→1 edge: on a **sourced** constraint every edge re-captures and the bit is clip-animatable — off = ride the source, on = pin where it stands, the deploy/recall idiom. An edge captures the node's **own current pose, one solve late** — after that frame's parent ride, never a source's or a target's pose, so arm it from a settled pose or the capture lands a step downrange. **Source-less it captures once** and nothing re-captures (the pose lives native-side; no serialized field, knob cycle, or component/GO bounce resets it). Unfreezing snaps back to the source-driven pose unless `RebakeOffsetsWhenUnfrozen=1`, which re-bakes the source offsets at the frozen pose so the object holds position and rides its sources from there.
- **`FreezeToWorld` is exclusive with any other constraint writing the same transform — give it its own node.** Co-located, the freeze wins and the other write is dead every frame with **no error** — the co-victim reads as a constraint that simply stopped responding. Splitting the freeze onto a *second*, source-less constraint over the same transform does not escape it: two constraints on one transform resolve in add order, so the later writer takes it. That contest is per **channel**, not per transform: a `VRCParentConstraint` + `VRCScaleConstraint` pair on one node write disjoint channels (position/rotation vs scale) and coexist exactly across the full scale range (measured in play; `vrc-patterns/object-sync`'s `Rig` ships that form). This is a placement rule for the bit, not anything damping-specific. **The pin belongs on a parent frame instead**, where either world-anchor idiom above holds a locomoting rig to within **one frame of parent motion with no cumulative drift** — a velocity lead that appears and vanishes with parent *acceleration*, not error that accrues — and everything below the pin then solves as if the avatar were standing still, a parent frame resolving before its child (position only; rotation and `VRCParentConstraint` untested).
- Source-weight animation is the universal multiplexer: N sources at weight 0, states select one. Weights are **normalized by their sum**, not clamped to [0,1] — only the ratios matter. Self-as-source at partial weight is a one-pole lag ("feel" damping): **`w_self` = 1, `w_target` = 0.05** means the *non-self* source carries the small weight and is the knob to turn for a given feel (`vrc-patterns/spring-damping` owns the formula, worked ratios, and tuning). A self-source drags rather than holds; the pin belongs on a parent frame (bullet above). Disabling a constraint stops it writing — the object keeps its current **local** pose and rides its parent from there (with a stationary parent that looks like a world freeze; it is not one). Normalization has **no magnitude floor**: residual weights near 1e-5 still command full-magnitude targets, so a rig that loses tracking swings a full offset in a stale direction before any state-machine response lands — pathological for a target that can teleport.
- A constraint with an **empty source list** writes nothing — it doesn't drive to a stored rest, it stops touching the transform, which then keeps whatever pose animation or authoring gives it (the "hold" idiom is this hands-off no-op). An active, locked constraint with a **populated** source list always writes, and what it writes is a blend **from the captured `*AtRest` pose toward the weighted source result, with `GlobalWeight` as the blender — and the rest pose resolves in the constrained object's parent frame**. So `GlobalWeight 0` (and a zero source-weight *sum* — `VRCParentConstraint`; other types unverified) re-writes the captured local rest every frame: the object rides its parent, **not** a world park. With rest = the authored local pose that is behaviorally invisible, but it is still a writer and stomps any animation or script moving that transform. That makes an animated `GlobalWeight` the clean composed show/hide lever for a follower riding an authored rest — 0 ≡ untouched hierarchy, 1 ≡ snapped to source, release restores rest the same frame with no stale offset. The truly hands-off levers remain the empty list and `IsActive` off. Per-axis `AffectsPosition/Rotation` masks decompose a transform into single-axis measurement/actuation channels.
- **A rotation-axis mask carves an Euler-Y channel, not a swing-twist one.** Masked axes hold the captured `RotationAtRest` (resolving per the bullet above — measured world-exact identity under a world-pinned parent, at every source attitude); the surviving Y channel writes the source's Euler-Y (ZXY) decomposition, so a tilted source bleeds only a sub-degree heading term (~0.3° at 60° of tilt) and stays stable through 90° of source pitch — then flips heading 180° past it as the decomposition changes branch, unreachable by human poses but real for inverted sources. Measured on the Y-only home mux `vrc-patterns/compositions/grab-sync` ships (its README §The arrangement carries why that mux is Y-only).
- **Offset frames differ by component and field, and neither field can carry a world park.** `VRCPositionConstraint.PositionOffset` resolves in the constrained object's **parent** space, so an offset meant as world-fixed rides the avatar's yaw. A `VRCParentConstraint` per-source `ParentPositionOffset` resolves in **source** space — world-oriented from a never-instantiated-prefab source, but the shipping client multiplies it by the avatar's **scale factor** (the editor/emulator SDK does not), so it lands at `s × offset` on every client. The one park that resolves identically on every client is a plain child **transform** under a zero-offset world pin, held at unit scale by §Scale's world-scale pin — **both halves are load-bearing**: the zero offset defeats the multiply, and the scale pin is what renders the child's local position as true metres rather than `s ×` them. `vrc-patterns/object-sync` §Rig carries the measurement, the scale-sweep test, and the shipped shape.
- A constraint's sources may be **its own children** — feedback loops are legal and resolve consistently each frame (the basis of the crawler/cage tracking patterns in `gimmicks.md`).
- **A target-hierarchy relation authors a cycle's stale edge, and outranks everything registration-dependent.** The first bullet's parent-first rule holds across a *mutual* source dependency too: when one constraint's driven target transform is a hierarchy **ancestor** of another's, the ancestor-target constraint solves in the strictly earlier group, so the ancestor side reads the descendant side exactly one frame stale — deterministically, where a flat pair's stale edge is an unauthored roll — measured black-box on isolated pairs and re-measured on a shipped rig under an adversarial gauntlet, with flat pairs rolling in the same scenes off byte-identical content. **So make a required stale read structural — give the constraint that must read stale the ancestor target, and nest the other's target under it**; no source-list addition or registration shuffle can then flip that pair. `vrc-patterns/grab-prop` §How it works ships the idiom (its sample cell is a child of the node whose constraint reads it) and owns the measurement and its counts.
- **A source-list edit can change behavior with every compiled value identical** — solve order derives from the source/target transform graph and never consults weights, and where the pair's targets carry no hierarchy relation (bullet above) a cyclic web's internal evaluation order is not a contract anything authored pins. Edge-case, but it has flipped a capture rig at weight 0 with all clips identical; the measured boundary and the safe composition move live in `vrc-patterns/grab-prop` §How it works.
- **`LatestValidExecutionGroupIndex` is a depth, not the cut — verify a cyclic rig by frame lag, never by comparing indices.** The index is a longest-path depth over the dependency graph; which edge of a cycle the solver leaves stale is decided separately, and the two disagree — a rig can hold an inverted index and behave correctly. `vrc-patterns/grab-prop` §Verifying the install owns the lag method and the measurement.
- **A depth ladder biases an undetermined cut; it does not override one an in-ring edge has already decided.** Depth is longest-path, so deepening a node drags everything downstream of it down too, and a ladder can never invert two constraints joined by a source edge. **The first remedy for any contested cut is the structural one — author the order with a target-hierarchy relation (bullet above)**; the ladder is for cycles where no such relation can be given, and its domain there is the intermittent break — good one session, bad the next off identical bytes. **A rig that breaks every session is structural: remove the in-ring edge instead** (`vrc-patterns/grab-prop` §How it works owns the repoint). The lag method that tells a biased cut from a decided one is `vrc-patterns/grab-prop` §Verifying the install (bullet above); the depth-ladder module that once carried it is retired, superseded by the structural fix.
- **`Locked` decides whether a constraint drives or holds, and the two inspector buttons bake different things.** An **unlocked** constraint re-derives its offsets from the current transform on every edit-mode solve, so it *holds its pose* rather than moving to its sources; `Locked` freezes the baked offsets and lets it actually drive (play mode behaves as locked regardless of the flag). The buttons differ in what they capture: **Activate** (`ActivateConstraint()`) bakes the **current** offsets — a driven object sitting 2 m from its source gets a −2 m offset, so activating changes nothing visually, by design — while **Zero** (`ZeroConstraint()`) clears the offsets so the object snaps onto its source, then re-bakes rest. Reach for Zero when the constraint should take, Activate when the current pose is the rest pose you want — and never Activate a **world pin** on a placed avatar: it bakes the avatar's scene pose into the source offset, the field the offset-frames bullet above says cannot carry a world park, so the "aligned" pin now lands `s ×` that bake on every client in every world. A world pin's correct serialized state is all-zero; if one has been disturbed, Zero it. Script-setting `Locked = true` captures nothing, leaving `*AtRest`/offsets at type defaults, so code building constraints must call one of those two (or set the offsets explicitly) or the constraint silently drives to the wrong rest.
- `Sources` is a bare field of **struct** type, and `IsActive` a bare bool defaulting **false** (the inspector's Activate button sets it). Reflection or `dynamic` access (`execute_code`) boxes the struct, so `Sources.Add(...)` mutates a copy and serializes nothing — no error, just `totalLength: 0` on disk and a constraint that never runs. `totalLength` is also where the editor and the client part: the editor solves every slot holding a transform, the client solves exactly the first `totalLength` slots, so a source written into a slot past the length (a `SerializedObject` write to `Sources.sourceN.*` that leaves the length alone) works in every play-mode pass and does nothing in-game (measured: a fourth position source an animator weighted moved a prop in play mode and nothing in the client until the length read 4). Only the first 16 sources sit in keyable slots (`source0`…`source15`, the ones an animator can reach); the rest live in `overflowList`. Script-built constraints: write `Sources.source0.*`, `Sources.totalLength`, and `IsActive` through `SerializedObject`, then re-read the saved asset — and note `Sources.totalLength` is invisible to a `NextVisible(true)` property walk though `FindProperty` resolves it (measured), so a dump-then-write flow omits exactly the must-write field and ships a constraint that never runs. Directly-compiled C# is NOT the escape it looks like: `source0`/`totalLength` are serialization names the list type does not expose to compiled `execute_code` either (measured) — `SerializedObject` is the one reliable write path for constraint sources. That is an *authoring* (serialization) trap only: **in play**, a constraint built entirely from compiled script — `AddComponent`, `Sources.Add`, config fields — simulates correctly, and a bare script write to an un-animated config field (`GlobalWeight`, `IsActive`) applies on the next solve (both measured). **Read a script-built constraint's placement in play, never in edit mode** — a script-added constraint never registers with the manager there (`IsConstraintRegistered` false with `enabled`, `IsActive` and the GameObject all true, and forcing registration does not start it), so it silently writes nothing while every serialized field reads correct; the same rig solves exactly on play entry (measured). A saved-and-reopened scene does not rescue it, which is what makes an edit-mode read look authoritative. What does not hold a script write in play is **animator binding** — the playable graph re-writes bound fields every frame, WD-default writes from off-state toggle layers included (`verify.md` owns that trap; it is not constraint-specific).

## Scale

Systems that size or place in world units must be scale-aware (avatar scaling is on by default). Read-only params: `ScaleFactor`/`ScaleFactorInverse` (ratio to upload height, for DBT multiplies), `EyeHeightAsMeters` (absolute metres, linear past the 5 m cap — the robust one), `EyeHeightAsPercent` (0–1, Motion-Time-compatible, valid 0.2–5 m only), `ScaleModified` (bool).

- **Scale is not the wearer's choice: the client clamps eye height into each world's allowed range**, force-scaling any avatar whose upload height falls outside it (readable live: OSCQuery `/avatar/eyeheight*`, `ScaleFactor`). A rig that breaks under scale therefore breaks **world-binary** — same avatar, most worlds fine, the rest dead — so a world-binary failure is a scale suspect before it is a tag, park, or network one.
- Scale multiplies every **parent-space** constraint offset, every constraint **source** offset (asset sources included — §Constraints' offset-frames bullet; the world-scale pin below protects the hierarchy under it, not a source offset on the pin itself), and every **contact shape** (§Contacts). A rig comparing an absolute world position against an avatar-frame offset diverges by `(scale−1) × offset-distance`; one whose senders and receivers scale *together* stays self-consistent and hides the defect.
- **The world-scale pin:** a `VRCScaleConstraint` sourcing a never-instantiated prefab asset (§Constraints' position-anchor trick) holds a subtree at world scale in one static component — offsets and contact shapes both, which no animator-side `ScaleFactorInverse` multiply can reach. Shipped: `vrc-patterns/anti-cull`, `vrc-patterns/object-sync`; Custom-Object-Sync pins its root the same way.

## Other load-bearing components

- **VRCHeadChop**: exempts chosen bones from first-person head shrink (scaleFactor 1 = full size in first person) — required for self-interactable face gimmicks, whose colliders and physbone chains otherwise collapse with the head. First-person-local only: mirror clones strip the component, remotes never apply it. An exempt bone is not left alone: the client re-places it every frame anchored to the **humanoid head's** live transform, so anything docked on an exempt bone follows the humanoid head wherever constraints or IK send it — and the chop **releases entirely once the target bone is roughly 0.5–1 m from the avatar root** (in-game measured; threshold unpinned, plausibly scale-relative). Worked entries — chop-exempt mouth anchor (`anchor-prop`), self-exempt face-grab chain (`head-deform`), proxy-head rig with the mirror-gated fake chop (`head-proxy`, gated via `mirror-detect`) — live in `vrc-patterns`.
- **VRCRaycast** — the one avatar component that senses **world geometry**: a bone-origin ray driving a `resultTransform` (usable as a constraint source; placed at the hit point and **oriented to the surface, `up` along the hit normal**, so it sources rotation as readily as position) and `_Hit`/`_Ratio`/`_Distance` animator params, with a Collision Mode selecting world or **player** layers. **Every copy runs its own ray and the player capsule exists only on its owner's client**, so each client raycasts a *different* world — the one structural fact that shapes whether a design can use it at all (`gimmicks.md` prices the per-observer affordance it buys). Everything below that is measured in one place rather than summarized here: **`vrc-patterns/selective-animation`** owns the layer masks, self-hit conditionality, miss semantics, per-rig aiming, and the emulator's limits on all of it.
- **VRCAnimatorLocomotionControl** `disableLocomotion`: freezes movement *and stops the player capsule from colliding* — a movement-locked player can be pushed through geometry ("reverse" collision). VRCAnimatorTrackingControl, VRCPlayableLayerControl: standard layer/tracking tools.
- **Particle system as world-collision sensor**: one immortal motionless particle + world collision (`minKillSpeed` ≥ its jitter) + `stopAction: Disable`, wrapped around an always-overlapping sender/receiver pair; the FX re-activates the GO each frame to re-arm. Radius must be tuned against the player capsule.
## VRCFury build-time reshaping

Framework model, choice, and ordering rules: `nondestructive.md`.

**Param prefixing pairs component and controller.** Non-global params get instance-prefixed (`GrabBone` → `VF157_GrabBone`), and the rewrite carries every **sensing component's own `parameter` field** — physbone, contact receiver, `VRCRaycast` — along with the animator conditions; generated layers are tagged `[VF…]`. Which names escape the prefix — and why a careless `globalParams` entry can unpair a raycast or physbone but never a contact receiver — is `gimmicks.md` §Packaging's. What binds here: the list is **per-`FullController` and binds both ends**, so a consumer module reading a name another module exported must match it on its *own* component too, or the rewrite prefixes the consumer's read and the two never meet.

**The Parameter Compressor.** Past **256 synced bits** the compressor engages — not a ceiling but a threshold VRCFury absorbs: it sets the overflowing params network-synced-**false** and time-multiplexes their values through one shared channel, rebuilding each on the remote clone via a parameter driver (so they update at a reduced rate). **Trap:** a compressed param reads *un-synced* in the baked ExpressionParameters yet still replicates — never infer sync state from the parameter asset alone. OSC-driven and `Add`-driven params stay uncompressed (tag a latency-critical param with an `Add` to exempt it). VRCFury records what it did in a `VRCFuryDebugInfo` "Parameter Compressor" component on the avatar root (bit totals, sync delay, batch counts) — read that instead of diffing builds. It fails loud only when even maximum compression can't fit.

**Build-time swaps and platform alignment.** `ApplyDuringUpload` swaps editor scaffolding for runtime config at build; a mobile build additionally aligns its synced-param order to the last desktop upload's on-disk sync data, so that set isn't a pure function of the avatar.

**Write Defaults conform.** A merged module's authored WD setting never reliably survives: every layer VRCFury manages takes the avatar's majority regime, Direct-tree and additive layers excepted and forced **ON**. Mode `Disabled` does not disarm that — it only holds the conform to VRCFury's own layers, where every other Fix-Write-Defaults mode reaches *all* of the avatar's.
