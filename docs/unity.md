# Unity

`AvatarProject/` is the sandbox Unity project (an untracked working venue — CLAUDE.md §Layout). Its Unity version is **VRChat-pinned — never upgrade** (breaks uploaded content).

Packages are VPM-managed and reproducible (constraints: workspace `CLAUDE.md`; commands: `bootstrap.md`).

## Unity MCP

Transport is stdio; Claude Code connects through our **`vrc-mcp-proxy`** (sibling repo), which pins and spawns the upstream MCP-for-Unity server and owns the tool allowlist plus known-lie corrections — a `[vrc-mcp-proxy]` note or refusal in a tool result comes from that layer (its README lists the behaviors). The server brokers to each Editor's bridge across recompiles/domain reloads. Registration, transport, and package-update wiring: `bootstrap.md`.

- Read editor state via **resources** (`mcpforunity://editor/state`, `project_info`, …); perform mutations via **tools** (`manage_scene`, `manage_gameobject`, … — permission-gated) or `execute_code`.
- After creating/editing scripts, check the console (`ReportConsole`) for compile errors before using new types (poll `editor_state.isCompiling` for the domain reload).
- The one `UnityMCP` server reaches every local Editor. With **2+ Editors connected and no pin it hard-errors, naming the instances**; a **single** Editor auto-selects. Still make `set_active_instance` with the **full** `Name@hash` the first Unity call of every session — the reliable way to pin routing for the whole session. The live instance table is injected into session context at start (SessionStart hook → `tools/unity-instances-hook.sh`); also queryable via the `mcpforunity://instances` resource. Hashes are path-derived cache keys — read them live, never copy them into docs or config.
- **One agent drives Unity at a time** (CLAUDE.md rule 9 owns the shape — a foregrounded subagent is sanctioned; the pin is per MCP connection and every subagent shares the session's one connection, so a subagent's pin outlives it — re-pin after it returns). The `unity_instance` parameter — the full **`Name@hash`** — routes a single call without touching the session pin (it works on `manage_editor`/`execute_code` despite the loaded schema not listing it), and a mutating snippet no longer carries its own venue check — `execute_code_venue_guard` owns that.
- If `UnityMCP` tools are absent: the Editor isn't open on the target project; the `vrc-mcp-proxy` sibling or `uv` is missing (a broken checkout gets **zero** UnityMCP — `bootstrap.md` steps 1-2); or Claude Code needs a restart.
- **Bring up an editor yourself** when none is live: match the project's `ProjectSettings/ProjectVersion.txt`, then `Start-Process` that `Unity.exe` — resolve its path from the Unity Hub registry (`%APPDATA%\UnityHub\editors-v2.json`, which covers custom install dirs) or the default `C:\Program Files\Unity\Hub\Editor\<ver>\Editor\Unity.exe`. `vrc-get resolve -p <project>` first if the VPM payload is stale. The bridge auto-starts on a cold open.
- **Trust the heartbeat, not the MCP window.** The Editor's *MCP for Unity* window can show "No Session" while the stdio bridge is up — a cosmetic desync; the `~/.unity-mcp/` heartbeat (what the SessionStart hook reads) is truth. But a stale or `reloading` heartbeat is live, not ready — the instance table lists liveness, so a console read (`ReportConsole`) is the real proof the bridge will serve.
- **Never switch to the Editor-hosted http transport.** It drops on every domain reload, and its toggle (`MCPForUnity.UseHttpTransport`) is a **machine-global** EditorPref shared by every project on this Editor version — flipping it hits all of them on the next restart.

## Agent-callable tools

The agent inspection harness (`agent-tools`) and the vendor→owned avatar kit (`avatar-tools`) are the static-method tools you call via `execute_code`; their per-tool contracts live in **`docs/unity-tools.md`** (read it before driving one). The two conventions every one of them shares stay here, since they govern how the whole surface is invoked:

**Invocation.** Every door in both kits is a `public static` method called via `execute_code`, but the **handle style splits by kit and family**, so read the call shape on the door's own row in `unity-tools.md` — every door carries one — rather than inferring a kind from the families here. `agent-tools` is string-handled — hierarchy paths, asset paths, names — with three of its asset doors adding a typed overload and `CheckAvatar.ScanAnchorSeams` taking a typed `GameObject` outright. In `avatar-tools`, the **asset-path** doors are string-handled (`ReportPackage`, `OwnMaterial`, `CheckHumanoidRig`, the compile/decompile family, `NormalizeExpressionClips`, the thumbnail doors), while the **scene-mutating transplant/upload family** (`ConformRenderers`, `CopyComponents`, `MoveComponents`, `GraftHierarchy`, `CopyDescriptor`, `FixViewpoint`, `RemapMaterials`, `ConstrainedDuplicate`, `UploadAvatar`) and the **controller-mutating** one (`CleanController`, `RepathClips`, `OwnControllerClips`) take typed `GameObject`/`Transform`/`AnimatorController` refs. `MatchHumanoidRig` is mixed (a path plus a `GameObject`). A third kind is neither a project handle nor a typed ref: a **session handle**, minted at runtime and dead when the play session ends (`GrabPhysBone`'s grab handle, `RenderThumbnailPlay.Shoot`'s poll tag) — a string only because a snippet cannot carry a typed ref to the next call. Namespaces: agent-tools under **`Ryan6Vrc.AgentTools.Editor`**, avatar-tools under **`Ryan6Vrc.AvatarTools.Editor`** — but the **assembly** capitalizes the acronym (`Ryan6VRC.…Editor`), so an assembly-qualified reflection lookup uses `Ryan6VRC` while the type namespace is `Ryan6Vrc`.

**Preview grammar.** Every mutating tool takes a default-off preview: **`whatIf`** when the tool can run its full plan and mutate nothing (preview == execute), or **`preflight`** when the operation can't be dry-run at all and only its preconditions are checkable (`MatchHumanoidRig`, whose reimport *is* the operation). The dividing line is *ran the plan and mutated nothing* vs *couldn't run the op at all* — not complete-vs-incomplete numbers (so `CopyDescriptor` stays `whatIf` even though its remap counts land only on execute). Each tool names its own mode in `unity-tools.md`.

## Geometry-change reconcile (reproportion / re-export)

Changing avatar geometry leaves Unity-side state stale — it holds frozen references or meters that do **not** track the new geometry. The `reproportion` skill sequences this; the durable facts:

- **Humanoid bind.** Frozen into the FBX `.meta` at rig time; it does not self-update. **Re-run `MatchHumanoidRig` after any geometry change** or the bind disagrees with the bones (folded hips); `CheckHumanoidRig` verifies it.
- **ViewPosition** (eye height) is an avatar-local **meters** vector — recompute on any height change or the viewpoint floats off the eyes (not sub-notice).
- **Absolute component dimensions** — physbone / collider / contact radii are meters; they don't scale with a rescale (drift linear in magnitude, negligible at small reproportions).
- **Prefab-persisted SkinnedMeshRenderer blendshape weights unlink (reset to 0) when a mesh is renamed or re-exported** — re-verify driven weights, and keep them coherent across meshes (an outfit's matching morph is often name-variant, e.g. `Bra_Breasts_big` ↔ `Breasts_big`). A Blender shape-key *value* crosses as the imported blendshape weight (see `blender.md`). Body-shape morphs can be set in Blender or here; keep one value per morph across meshes — the coherence invariant the `reproportion` skill (*Realizing shapekeys*) owns.

## Non-destructive avatar build

Modular Avatar (on NDMF), VRCFury, the **d4rk Avatar Optimizer**, and the **Limitex (LAC) texture compressor** compose non-destructively — nothing touches the editor scene; a throwaway copy is rebuilt at Play/upload (`nondestructive.md` owns the model). The Unity-side consequence: there's no Add-Component menu over MCP, so discover a tool's exact component type with an `AppDomain` `MonoBehaviour` scan — `d4rkAvatarOptimizer`, `dev.limitex.avatar.compressor.TextureCompressor`, VRCFury features under `VF.Model.Feature.*` held by a `VF.Model.VRCFury` component.

Validate the baked result without uploading: **enter play mode** — it runs the whole non-destructive stack on the transient play copy, removed on exit (`nondestructive.md` owns the claim). One session is both the baked read (the built clone + `VRCFuryDebugInfo`) and the live drive (av3emulator). The **play-entry gate** is enforced on entry; `verify.md` owns the preconditions, `emulator.md` the recipes.

## Reading serialized assets

A `.prefab`, `.unity`, `.asset`, `.controller` or `.fbx.meta` is a partial view of a composed system, and hand-reading one is where false "broken / disabled / null" claims are manufactured. Let the doors read the avatar (`unity-tools.md`, `animator.md`); this section is the vocabulary for when you read the YAML anyway. The rule about what such a read may then be used to assert is `verify.md`'s.

- **`fileID: 0` is mostly benign, and its generators are enumerable.** A VRC constraint's sources serialize as a fixed 16-slot array, so an unused slot is padding rather than a null ref — on a real avatar prefab that one generator can be most of the file's hits. The frameworks then spell "auto" as blank: a VRCFury blank `renderer` means every matching renderer on the avatar, `rootTransform: 0` means self, and a legacy single-slot `objRef` sits beside the populated plural list that superseded it (`nondestructive.md` §Reference hardening owns the framework half). Counting `fileID: 0` measures none of this; `CheckAvatar` names the refs that genuinely resolve nowhere.
- **A reference can be complete only in the scene, or only at build.** A slot left null on a prefab asset is routinely filled per scene by the instance's `m_Modifications`, so the asset is the wrong place to read it — and anything derived from the avatar is read off the baked result, never the source asset (`nondestructive.md`).
- **`PrefabUtility.GetPropertyModifications(instanceRoot)` is the one-call complete read of an instance's overrides, and a hand-rolled comparison is scoped to whatever fields it happens to type.** A diff over `activeSelf` and blendshapes prints nothing and reads as "no overrides" on an instance carrying three material ones. The same call confirms an override was **recorded at all**: Unity stores a modification only where the value *differs* from the parent, so a pin deliberately set to the parent's current value is never recorded and evaporates the moment the parent moves. Pin after divergence, then verify the entry exists. The inverse misreads too: `RevertObjectOverride` leaves the entry in place, so entries present is not the same question as values differing.
- **fileIDs do not identify what they look like they identify.** Inside an FBX they are derived from name + type, so every bone named `Head` in every model carries the same id: "same fileID ⇒ same bone" is false across models. A prefab **variant** remaps ids, and the remapped values appear in no `.prefab` at all, so following a reference by search stops dead at the variant with nothing signalling that it did.
- **The humanoid mapping lives in the importer, not the hierarchy.** `ModelImporter.humanDescription` in the `.fbx.meta` decides which transform is the humanoid `Head`, and it may name a proxy that is a *sibling* of the skinned bone. Every prefab, scene, controller and clip then reads consistent with the wrong answer, and no scene-scoped digest sees it either; `CheckHumanoidRig` is what reads the importer.
- **A GUID index built from the venue folder alone manufactures dangling references.** Each venue mounts our sibling packages by `file:` path in `Packages/manifest.json`, so their assets live outside the venue tree entirely — a `.meta` sweep that walks `<venue>/Assets` and `<venue>/Packages` resolves none of them, and every `vrc-patterns` prefab an ordinary scene instantiates then reads as absent. That is precisely the evidence a "this scene is rotted, delete it" verdict rests on, and the scenes it condemns are the ones composing our own shipped entries. Index the mounted paths too, or take the verdict from `CheckAvatar` / `CheckPackage`, which resolve through the asset database and cannot make this mistake.
- **One asset file can hold more than one document.** A submenu is a second YAML document inside the same `.asset`, so a read that stops at the first document reports a menu the avatar does not have.
- **Behavior spans artifacts that name each other nowhere.** A parameter is declared in one asset, written in a second, read in a third, and joined across separately-merged controllers by VRCFury's `globalParams` (`gimmicks.md` §Packaging owns it) — so deciding whether one toggle exists can take five artifacts, none of which is wrong on its own.

## Sharp edges

- **Bridge "Connection closed" on the first call** after the Editor's been idle or just reloaded — retry once; it reconnects. The first read-only call **immediately after a successful pin** can return a similar false negative (stale connection) — `refresh_unity` or one retry unsticks it; don't read the pin itself as failed. An instance-not-found error on a live Editor is a third case and mostly no longer yours to diagnose: `vrc-mcp-proxy`'s `instance_not_found_note` reads the heartbeat at fire time and says whether to re-pin, wait out a reload, or go look. **Under a heavy import it can only tell you to try** — the heartbeat is written from the main thread the import is blocking, so a busy Editor and a closed one read alike from outside; re-pin rather than going to look, and never re-issue the import to "fix" it before checking on disk whether it landed.
- **`execute_code` is async-blind.** An async Unity call (e.g. `AssetDatabase.ImportPackage`) returns before the work finishes — verify the result in a separate call before chaining dependent ops. For heavy `.unitypackage` imports use the transport-survivable `ImportPackage` door (`unity-tools.md`) instead.
- **`EditorApplication.delayCall` is pumped only while the Editor is the foreground application** (`InternalEditorUtility.isApplicationActive`), where `EditorApplication.update` ticks either way. An MCP-driven Editor is normally unfocused, so a registered `delayCall` queues indefinitely and then fires on the click that focuses the window. Neither `execute_code` nor its dynamic assembly is involved — a `UnityEditor.CoreModule` delegate queues identically, and an `execute_code` lambda fires next tick once focused — so re-registering from a compiled assembly is not a workaround. A domain reload discards the queue silently, without running it, `[InitializeOnLoad]` package code included. Defer off `EditorApplication.update` instead; a queue already parked by someone else's code can be drained on demand by pumping `EditorApplication.Internal_CallDelayFunctions()` from an `update` hook — the remedy that works even when focus can't be made to land.
- **After a domain reload, VRC constraints stop solving in edit mode until something re-registers them — and the silence reads as "this rig has no constraint behaviour".** `VRCConstraintManager`'s registry is a static cleared by the reload; the components do not re-add themselves, so `_constraintsManaged` sits at 0 while the scene holds dozens, every one enabled with `runInEditMode` true and `CanExecuteConstraintJobsInEditMode` still reporting True. Nothing solves and nothing says so. A `manage_packages resolve_packages` is enough to trigger it, so it lands squarely on the workflow that repoints a package mount at a worktree and then measures. Toggling a component's `enabled` does **not** re-register; `EditorUtility.RequestScriptReload()` does. Check the registry count before trusting any edit-time constraint measurement — a pinned rig sitting on the avatar instead of at its pin's source is the tell, and read the wrong way it retires a real defect as unreproducible.
- **A play entry issued while a script compile is pending wedges both, indefinitely, with no error and no modal** when the Editor preference *Script Changes While Playing* is **Recompile After Finished Playing** (`ScriptCompilationDuringPlay` = 1): the pref defers the compile until play ends, play entry waits on the compile, and the Editor sits with `isCompiling` and `isPlayingOrWillChangePlaymode` both true, `CanReloadAssemblies()` false, and nothing in the console — distinguish it from a slow build by the compile artifacts (`Library/Bee`, `ScriptAssemblies`) not moving. Break it by clearing the queued entry (`EditorApplication.isPlaying = false`), then giving the window one brief real foreground focus to pump the parked compile; re-enter play after `isCompiling` clears. Programmatic focus is the unreliable half: `WScript.Shell.AppActivate` returns success while `isApplicationActive` stays false — the form measured to land is a synthetic Alt keypress (`keybd_event 0x12` down/up) immediately before `SetForegroundWindow`.
- **`GameObject.Find` never returns an inactive object; `transform.Find` walks inactive children fine.** Every restore-a-toggle workflow NREs on the former unless it holds a reference. The `manage_gameobject` half of this trap is annotated at fire time by `vrc-mcp-proxy`'s lookup-miss note; this half returns null from a *successful* call, so there is no failure response to annotate and it is stated here.
- **A destroyed handle answers from itself, not from the scene, so re-testing it is not evidence the destroy landed.** Unity overloads `==`/`!=` on `UnityEngine.Object`, so after `DestroyImmediate(t)` the cached `t` reads `== null` true whatever the scene now holds — the check cannot fail — and a snippet whose tail-check is `t != null` reports failure on every successful destroy. Re-query for the real answer: `GameObject.Find(path) == null`, or a fresh `transform.Find` from a live parent. Reference identity bypasses the overload in the other direction — `ReferenceEquals`, `??`, `?.` and `is null` all read a destroyed object as live.
- **`Type.GetType("Name, Assembly")` returns null in `execute_code` for VRCSDK / emulator types** (`LyumaAv3Runtime`, `VRCAvatarDescriptor`, `PipelineManager`) — the assembly-qualified lookup doesn't resolve them. Find the type by an `AppDomain` scan matched on name (the pattern §Non-destructive uses to discover tool component types), or grab a live instance with `FindObjectsOfType`.
- **VRCFury components build cleanly from `execute_code` despite `VF.Model` being internal**: `AddComponent(Type)` + `Activator.CreateInstance(type, true)` + reflection field-sets; `GuidWrapper.objRef` is public (leave `id` empty — VRCFury syncs it); fresh model instances auto-stamp `version` via serialization callbacks, so no manual versioning. Enum semantics must come from VRCFury source (`ObjectToggleAction.Mode.TurnOn = 0`); the approach covers FullController, Toggle, ApplyDuringUpload, and FixWriteDefaults.
- **Reading a vendor texture's pixels never goes through `TextureImporter.isReadable`** — the toggle + reimport round-trip is a *write* (net-modified `.meta` files under `Assets/Vendor/`, unsanctioned per `LAYOUT.md`). The non-mutating read is `Graphics.Blit` into a temporary `RenderTexture`, then `ReadPixels` from it.
- **A vendor system's blanket `SaveAssets()` rewrites incidentally-loaded vendor assets far from its own folder** — a merely-referenced controller churned content-clean, Resource renderTextures re-serialized. After any vendor-system apply, sweep the vendor tree for just-written paths (mtime — the venue has no git to diff) and triage each: expected generated output vs. incidental rewrite vs. real mutation (`LAYOUT.md` §Vendor mutation).
- **A vendor tool whose only interface is an inspector button** is drivable headlessly: `Editor.CreateEditor` on its target, then reflect and call the inspector's apply methods in the button's exact sequence. Proven, but it couples to vendor internals — re-verify the sequence against the vendor source after any tool update.
- **Editing asset/package files outside Unity** leaves the asset DB stale ("Build asset version error"); clear the console + `refresh_unity` (mode=force, scope=all).
- **A `Local` UPM package is a live checkout of a public repo.** Each venue mounts our siblings by `file:` path, so an ordinary save on a scene instance sourced from one writes into that repo's working tree with no editor-side sign you left the venue — a `git status` in the sibling is the only detector. Mutability by `PackageInfo.source`: `Local` and `Embedded` (SDK, Modular Avatar) writable, only `Registry` (`Library/PackageCache`) immutable. Deliberate writes under `Packages/` are `LAYOUT.md`'s policy call.
- **Scene creation over `execute_code` is `NewSceneMode`, not `NewSceneSetupMode`**; `manage_scene create` emits an **empty** scene — the server's "always include a Camera and main Light" instruction is fiction. It also has **no unsaved-work gate**: a `Single`-mode create over a dirty scene discards it silently. When an unrelated dirty scene is loaded in a shared editor, build **additively** and clean up your own roots after — that protects the editor's other work, not yours: the next `Single`-mode `load` or `create` discards your additive scene too.
- **`isDirty` does not tell you whether a scene's content matches its file, in either direction.** Modular Avatar stamps a version tag and its resolved object references into a prefab instance's overrides on load, dirtying a scene with nothing of yours behind it (it does not recur, and the emulator is not what does it) — and the same stamp lands on other scenes without setting the flag at all, so a scene reads **clean** while its live content diverges from disk. An ordinary edit can sit behind a clean flag too. "Clean" is therefore never a licence for a discarding reopen; the only honest answer is a content comparison — serialize the live scene to a throwaway copy and diff it against its file, which is what `RenderThumbnailPlay.Run()` now gates on, naming the differing properties when it refuses. Scope any such comparison to scenes under `Assets/`: saving a scene fires every `sceneSaving` handler in the project, and NDMF's and MA's preview scenes destroy their own roots when they are the scene being saved. **Save** to settle a real difference; never clear one by reopening from disk, which *is* the discard. A save is scene-wide, so it commits everything else in that scene too — ask before saving a scene that is not yours; a venue is untracked, so there is no diff to recover from.
- **A `Grep` sweep over a venue's `Assets/` silently omits `Assets/Vendor/`, and reports the remainder as the whole.** The venue's own `.gitignore` drops the vendor tree — over 90% of the venue's files, every vendor avatar, outfit and material among them — and ripgrep honors it because the venue sits under the workspace's `.git`, so a GUID or reference sweep returns a confident zero with nothing in the result saying a tree was skipped. ripgrep never filters the root you *name*: `Grep` aimed straight at `Assets/Vendor` answers correctly, and `rg -uu` (or `Select-String`) by absolute path is the in-session override. The corollary is that two sweeps rooted at different depths of one tree disagree without either reporting it, so pin the root before trusting a count. Binary extensions are hidden everywhere under `Assets/`, which costs enumeration as well as content: "does this texture exist" also answers falsely. The durable fix is a re-include in the venue's `.ignore` (`new-project.md` step 1); `venue-ignore-audit` owns the ignore-file mechanics and measures what a venue is actually hiding.
- **`Grep` cannot see any VPM package's source, in any venue — and that is the tree Rule 10 sends you to for package behavior.** `Packages/.gitignore` prunes every package directory (`/*/`) bar `com.vrchat.core.*`, so a venue-rooted sweep reaches well under 1% of what is there and a "what does Modular Avatar do with X" search returns the same confident zero as the vendor case above, for Modular Avatar, VRCFury, NDMF, the optimizers and the shaders alike. The escape is the same: ripgrep never filters the root you *name*, so `Grep` aimed at one package directory (`Packages/nadena.dev.modular-avatar`) answers correctly, and that is how package source is meant to be read. A venue-root `.ignore` cannot re-include it — a deeper ignore file outranks it, so only a `Packages/.ignore` holding `!/*/` would — and the live venues leave it hidden on purpose rather than add over ten thousand files to every venue-wide sweep.
- **`AssetDatabase.FindAssets` matches names, not filenames.** The filter splits on whitespace **and on `*`** — `*` is a separator, not a wildcard — and each token must be a substring of the asset's name **with the extension excluded**, `.` matching literally. So an `*.ext` term never selects by type: zero hits where no name embeds that text, and a confident set of wrong assets where some do. Filter by kind with a `t:` term, keep free text for name fragments, and when you already know the path use `AssetDatabase.LoadAssetAtPath`. Through `manage_asset search`, `vrc-mcp-proxy`'s two search notes say this at fire time and cover the **scope** arm besides — a `path` that is not a valid folder is dropped rather than refused and the search goes project-wide, a `Packages/…` scope always (upstream force-prefixes `Assets/`). The scope note can still miss: paging hides out-of-scope hits, and its empty-result check needs a venue this proxy can resolve. So read every hit's own path on any scoped search.
- **`AssetDatabase.MoveAsset` leaves the drained wrapper folder inconsistently** — self-cleaned in some cases, lingering until a later asset-database refresh in others. Re-list the destination after every relocate rather than assuming either.
- **Vendor GameObject names carry trailing spaces** (`"Menu "`, `"Ears "`) that silently break exact-path lookups (`transform.Find` / `GameObject.Find`) — copy the name from an inspector dump, or match by trim/`StartsWith`, rather than retyping it.
- **An FBX's external-material remap applies only at import time.** A model imported before its `.mat` targets exist (costume package before a separate MaterialPack) caches empty slots that no later import re-triggers — force-reimport the FBX. **Do not look for `materialLocation: External` to recognize one**: that is the legacy extract-to-files mode, and a modern remap lives in the importer's external-object map while `materialLocation` still reads `InPrefab` — measured across every remapped vendor model in AvatarProject, so the `External` reading is the rare one. `CheckPackage` flags both arms and tells them apart: a remap whose entries resolve yet land on no renderer is a stale import (force-reimport), one that resolves to nothing means the pack was never imported (import it *first*, then reimport). Empty slots on a model whose entries all landed are a third thing and no fault at all — other submeshes, which a reimport cannot clear. The `import-vendor-asset` skill owns the procedure.
- **Reparenting a prefab instance's internal children silently no-ops.** `Transform.SetParent` on an object owned by a prefab instance reverts with no error — restructure before prefab conversion, or edit the asset via `PrefabUtility.LoadPrefabContents`. Verify by `childCount`, not `SetParent` calls. The no-op is specific to reparenting: **deleting** such a child works (even plain `DestroyImmediate`) and records a revertible removed-GameObject override on the still-packed instance — the Overrides dropdown, or `PrefabUtility.GetRemovedGameObjects()[i].Revert()`; the asset on disk is untouched.
- **VRCFury components take no prefab-instance overrides — all of them.** Every VRCFury inspector derives from a sealed base that disables itself on an instance ("Edit in Prefab"), and `VRCFPrefabFixer` reverts *every* override on a `VRCFury` feature component at play-entry and SDK build start. Replace rather than override — removal is supported (previous bullet): add your own component carrying the feature's `content`, destroy the shipped one.
- **A fully-unpacked FBX instance saves as a Regular prefab, silently.** `SaveAsPrefabAsset` mints a **Variant** only while the root is still a prefab instance of the FBX; unpacked, the save succeeds with no error and the asset stops tracking the FBX — the next re-export ships a stale rest pose (mesh bindposes move, the prefab's transforms don't). Don't unpack during a build-up (added GOs and components are legal instance overrides, and so is destroying them); after converting, assert `PrefabUtility.GetPrefabAssetType(prefab) == PrefabAssetType.Variant`.
- **Stale skin deform is `RenderAvatar`'s check to catch, not yours to hand-rule-out.** An unfocused post-play editor or a pending script reload can serve stale skin deform to every live camera while weights read current; `RenderAvatar` refuses or certifies with `canary=live`, so a hand-rolled render (ad-hoc `Camera.Render()`, Scene view) carries no such gate — pair it with `SkinnedMeshRenderer.BakeMesh`, which stays truthful throughout, and note `SkinnedMeshRenderer.bounds` reads an uncomputed `(2,2,2)` placeholder while the editor is backgrounded. Mechanism and residuals: `agent-tools`' `Tests/Editor/RenderAvatarFreshnessGate.md`.
- **Entering play blocks the Editor main thread** while the non-destructive build runs (NDMF/VRCFury/d4rk/LAC): `editor_state` freezes and reads time out for ~minutes on a heavy avatar; an `execute_code` issued during it queues and returns once the build frees the thread — unless the build raises a modal (next bullet). Batch play-mode work; re-entering play re-runs the whole build. (The gate guarding entry is `verify.md`'s.)
- **Anything blocking the Editor main thread inside `execute_code` strands the caller** — the queue drains on `EditorApplication.update`. A build call that times out means **list dialogs, don't retry**: `Process.Responding` stays `True` under a modal, so it cannot tell you which case you are in.
  - **A modal.** The build pipeline raises many, and none are suppressible — VRCFury has no batch/pref/silent seam and the SDK's "Preprocess Callback Failed" is unconditional, so don't go looking for a flag. Read and press them from outside with `tools/unity-dialog.ps1`. The examples are not only VRCFury's Write-Defaults prompt: **an open prefab stage wedges play entry** on "Risk of unwanted modifications" whenever its content carries `[ExecuteInEditMode]` — every VRC constraint and MA component qualifies — and then chains a second "Prefab Has Been Modified" wedge on exit. The script clears both. The build is not the only riser: **a vendor tool's update check fires a modal at editor startup** when its window rides the saved layout — before any bridge exists, so from outside the editor never came up at all (no heartbeat, nothing to call) rather than stopped responding. `agent-tools`' `VendorDialogGuard` pre-arms the known once-per-session checks (MochiFitter's) so the dialog never opens; for an unknown one, `unity-dialog.ps1` still clears it, and closing the vendor window before the layout saves removes the trigger.
  - **`.Result`/`.Wait()` on an awaited Task** — Unity's SynchronizationContext posts the continuation to the thread you are blocking. Unrecoverable; kill the editor.
- **A collapsed retry is a mutation you cannot assume once.** The transport re-sends an identical `execute_code` payload up to 6× and Unity drains every copy on the first tick after a block clears; the proxy guard collapses that to one execution plus `[proxy-duplicate-suppressed]`, whose text names which of the three outcomes that one run had. **This is not a long-block phenomenon** — it fires on ordinary short mutating calls (a `SetActive`, a `SaveScene`, a `CleanController`). So the burden is standing, on every mutation you issue: make it idempotent where you can, and re-verify the state afterwards rather than reading a returned value as proof it ran once.
- **`-batchmode` auto-cancels dialogs**, logging `Cancelling DisplayDialog: <title>` — a headless build fails loud on that line instead of wedging, and the cancel never mutates WD (VRCFury resolves to Skip).
- **`Unity.exe` is GUI-subsystem and does not block under `& exe`** — use `Start-Process -Wait` for headless batchmode runs.
