# The Av3Emulator harness

Driving and observing an avatar in play mode with Av3Emulator — the emulator rung of `verify.md`'s method (read that first for the bar and the evidence rules; the play-entry gate is enforced there too). `unity.md` owns the `execute_code`/MCP plumbing these recipes run on; `runtime.md` is the physics being verified; `osc.md` owns the wire in full.

## Setup

**Emulator control object enabled** — the emulator does not auto-spawn; the scene needs an enabled `Avatars 3.0 Emulator Control` object (the `LyumaAv3Emulator` component). **Tools → Avatars 3.0 Emulator → Enable** creates it, per-scene — no scene ships it pre-enabled, so run the recipe yourself (play then spawns the three runtimes). The play-entry gate (`verify.md`) does not check for it — absence is a legitimate bake-only check — but driving the emulator without it spawns no runtimes and the harness reads empty.

And capture every observation — runtime reads, `RenderAvatar` shots — **before exiting play**: exit reverts the scene to authoring state, so anything captured after proves nothing about driven behavior.

## Runtimes

On play the emulator spawns three `Lyuma.Av3Emulator.Runtime.LyumaAv3Runtime`: local (`IsLocal`), MirrorReflection (`IsMirrorClone`), ShadowClone (`IsShadowClone`). Each holds `Floats/Ints/Bools` lists (`.name/.value/.synced`) plus built-in input fields (`GestureLeftIdx`, `Viseme`, `TrackingType`…). Get the local one:

```csharp
var rts = UnityEngine.Object.FindObjectsOfType<Lyuma.Av3Emulator.Runtime.LyumaAv3Runtime>();
Lyuma.Av3Emulator.Runtime.LyumaAv3Runtime local=null;
foreach (var rt in rts) if (rt.IsLocal) local = rt;
```

The three runtimes are **co-located at the same origin** and differ only by layer: local on **`PlayerLocal`**, the clones on `Player` / `MirrorReflection`. So `FindObjectOfType<VRCAvatarDescriptor>` and a name match both return whichever came first — often a clone (culled/fossil), not the local; always select by `IsLocal`. A scratch camera capturing the local **must cull to the local's layer only**, or a co-located clone draws over it (the ShadowClone renders opaque). Cull by the local runtime GameObject's **actual layer number** (`1 << local.gameObject.layer`), **not** `1 << NameToLayer("PlayerLocal")` — the VRChat layer *names* are unset in a bare project (`NameToLayer` → −1, a broken mask), though the emulator still separates the runtimes onto distinct numeric layers. Disabling a clone GO does **not** stick — the emulator re-enables it every frame; cull by layer instead.

## Drive / observe

For menu/expression **float** inputs write **`.expressionValue`** on the local runtime's param, **not `.value`** — the runtime rewrites `.value` from `.expressionValue` each frame on every param in the baked **expression-parameters asset** (the gate is asset membership, not the `synced` flag — `ParameterNames` in source), so a `.value` write silently reverts on an asset param, synced or not (it holds on controller-only params, which hides the trap); `.expressionValue` drives both. **Bools have no `expressionValue`** — a `BoolParam` drives via `.value` (change-detected against `lastValue`), but not reliably on a **synced+saved** bool: one write reverted between calls and a later identical one held, uncharacterized. Re-assert and re-read rather than trusting the first write. (A driver-written *output* also reverts each frame, by design.) It lands next tick. Read outputs from the runtime lists, scene transforms/blendshapes, or `ContactReceiver.paramValue` — matching the observable to the output channel (material / transform / blendshape / GO-active), or a naive scene-diff misses it. **A driven material property lands in the renderer's `MaterialPropertyBlock` in play too** — not just the edit-mode tick below — so read it with `GetPropertyBlock`, never `.material`/ `.sharedMaterial` (which return the authored asset value → false negative).

**Observation channels — don't cross them.** Three output kinds live in three places. **Driver** outputs (`VRC_AvatarParameterDriver` Set/Add/Copy — a debounce flag, codec bits) land in the runtime's `Bools/Floats` mirror: write the input (per §Drive/observe), read the output there. **The mirror is an input register, not a readback**: it pushes to the playable only on change, and nothing ever reads the playable back, so any value the emulator does not itself write through the mirror sits there at its initial value forever with no error. Two kinds bite. **Blend-tree / AAP** outputs (a Direct-tree smoother's feedback float) are never written to the mirror — read them off the live animator by setting `local.DebugDuplicateAnimator = VRCAvatarDescriptor.AnimLayerType.FX`, then `avatar.GetComponent<Animator>().GetFloat("<VF##_>name")` (VRCFury prefixes the param). But the debug animator **runs without the avatar's init drivers**, so drivers don't execute on it: read driver outputs from the mirror with debug **off**, AAP outputs from the debug animator with debug **on**, never both in one session (exiting play resets the mode). Crossing them is why a working codec reads all-zero. The second kind is **a built-in whose declared type disagrees with the emulator's**: `LyumaAv3Runtime.BUILTIN_PARAMETERS` types `IsLocal` as Bool and the per-frame apply searches only the list matching that type, so a controller declaring `IsLocal` as a **float** lands in `Floats`, which that pass never touches — the inspector reads 0 for the whole session while the playable holds whatever default the controller declared. Reading the playable directly (`AnimatorControllerPlayable.GetFloat` over the runtime's `playables`) settles either kind and needs no debug-animator mode switch, at the cost of reflection — that field is private.

## OSC — a fourth channel, and the only one reaching outside the process

`local.EnableAvatarOSC = true` on the local runtime opens a socket on VRChat's own ports and binds it to that avatar, nothing to author first; `tools/osc-probe.py` drives and dumps it, standard library only. The contract is VRChat's address space rather than emulator internals, so the same script drives a real client unchanged — the reason to build a re-pointable harness here. It carries what the mirror will not: receiver- and raycast-written parameters reach the wire even when no expression-parameters asset names them. Two things to know before driving anything. **Argument types are exact and a mismatch is usually silent** — an int never writes a float parameter, and on that animator-only path nothing logs the dropped write. And **drive a value once per frame, then read**: every datagram arriving in a frame is applied in order, so a set-and-clear burst lands as two writes rather than collapsing. Same crossing rule as above — an inbound write and the `.expressionValue` route are two writers to one value, so use one per session. `osc.md` owns the wire, the `/input/` inventory, and the exactness rule in full.

**Choosing this channel over the runtime lists.** Route a claim here when it is about **parameters over time** — a latch holding, a pulse's width, when a value settles — or about a rig a real OSC client will drive: an out-of-process listener timestamps a change-only stream, so it needs none of the in-process frame choreography below, and the drive path has no `.expressionValue`-versus-`.value` hazard. Stay on the runtime lists for everything structural: contacts, grabs, local-vs-clone diff, separating driver outputs from AAP outputs, and any single-shot read where the mirror is already in front of you. Two things the choice does not buy. It is **not reflection-free** — `EnableAvatarOSC` is a field on the local runtime, so the same runtime-selection preamble runs first either way. And the script's portability is not the *claim's*: addresses carry the parameter name verbatim where a client rewrites it, so a name containing a space resolves one way here and another in game (`osc.md`).

## Pure controller math skips play mode entirely

When a compiled controller's outputs are only AAPs / blend-tree math — a smoother, a math idiom, a frametime rig, with no drivers, contacts, or sync — host it on a bare `Animator` and tick `Animator.Update(dt)` in edit mode: `SetFloat` the inputs, tick N frames, `GetFloat` the outputs. Deterministic, exact `dt` (a frametime rig reads it exactly), one `execute_code` call, and the inputs need not be synced params. Faithful because AAP writes and blend-tree evaluation are stock Unity, identical to the FX playable — **but not for what an AAP does once a state stops writing it**, where the two disagree (`runtime.md` §Animator): take release and persistence questions to play. Two traps: **material** animation lands in the renderer's `MaterialPropertyBlock` — read `renderer.GetPropertyBlock(mpb); mpb.GetVector(prop)`, not `sharedMaterial` (which stays at the authored default and reads as a false negative; clone the material onto a temp renderer so no shared asset is touched); and cross-layer AAP writes propagate one frame late, so a multi-layer feedback loop (a fixed-step linear smoother) limit-cycles and a feed-forward chain settles only after ~depth frames — read feed-forward outputs at steady state.

## Two-call assertion

Frames advance only between calls; persist across them in `EditorPrefs`, editor-local — delete the key after:

```csharp
// Call A: baseline + stimulus
UnityEditor.EditorPrefs.SetString("k", idx.localRotation.eulerAngles.x.ToString());
local.GestureLeftIdx = 1;
// Call B: sample + verdict
float d = UnityEngine.Mathf.Abs(UnityEngine.Mathf.DeltaAngle(
  float.Parse(UnityEditor.EditorPrefs.GetString("k")), idx.localRotation.eulerAngles.x));
string verdict = d > 10f ? "PASS" : "FAIL";
```

## Edit-mode VRC constraints — the venue, not your wiring

**A scratch VRC constraint that doesn't move is usually the venue, not your wiring.** VRC constraints *do* solve in edit mode, but only once registered with the dynamics manager and only when the dynamics scheduler ticks — and in a cold-opened editor driven purely over MCP, neither is guaranteed: a freshly `AddComponent`-ed constraint **and** the scene's long-resident inspector-authored ones can all read unregistered and sit still no matter how correctly they are wired. Ordinary editor operations also drop registration silently — **`PrefabUtility.RevertPrefabInstance` deregisters the constraints under it** (measured), which is why a reverted rig looks frozen at a stale rest pose until a scene reload or play re-runs its `Start`/`OnEnable`. Its serialized data is *not* stale: after a revert the offsets read back exactly as the prefab authored them, and re-registering solves correctly from those values. So never read "my scratch constraint didn't move" as a bad `Sources` write, a missing `Locked` bake, ignored offsets, or corrupted rest data (all real and separate — `runtime.md` §Constraints). Force one deterministic edit-mode solve instead: `VRCConstraintManager.RegisterConstraint(c)`, then `VRCDynamicsScheduler.UpdateConstraints(finalizeImmediately: true)` — measured, a zeroed constraint snaps onto its source within that same call. Each later source move needs another pump; the automatic per-tick solve an interactive editor gives you does not reliably happen in an unfocused or headless session (the sibling of the unfocused-render throttle). Both entry points are non-public, but that is not what keeps this a probe rather than a tooling substrate: it **simulates in edit mode what play mode does faithfully**, so tooling it would freeze a substitute for the venue that settles the question — when the question is *behavior* rather than wiring, verify in play. Read the rule that way and not as "non-public means don't build": accessibility is a drift-risk input, never a build-or-don't gate. `PhysBoneManager.AttemptGrab` and `contactPlayerId` are equally non-public and ship as recipes below, because they operate *inside* the faithful venue.

## Sub-second timing needs in-process capture

MCP round-trips can't hit sub-second timing. When the observable is a *parameter*, don't start here: §OSC times it from outside the process and needs none of this choreography. For everything else, two working shapes: register an `EditorApplication.update` lambda in one `execute_code` call that `Debug.Log`s a tagged line every N frames (read back via `ReportConsole` with the tag as `filterText` — passing the tag is also what exempts the series from `collapseDuplicates`, since identical repeats are exactly the signal here), putting any same-call choreography — detect a state flip, apply a stimulus M frames later — inside the callback; or `AddComponent` a scratch recorder MonoBehaviour that buffers per-frame rows for later dump. And **don't assume a frame rate**: a focused editor in play mode can run 200+ fps while unfocused it throttles to ~12 — if timing matters, measure it from your own log. `Application.targetFrameRate` is a deliberate probe in the other direction: throttling to ~5 fps exposes clip curves whose value windows are narrower than a frame (an animator evaluates curves only at frame samples, so a few-frame pulse can fall between evaluations and silently never fire).

## Remote clone

`local.CreateNonLocalClone = true` spawns a non-local copy. Recipes and traps, one per paragraph:

**Judge the spawn from `local.NonLocalClones`, never from the flag or the selection idiom.** Two things make a working spawn read as a failed one, and together they can retire a verification that was fine: the flag is consumed — the runtime clears it *before* instantiating — so reading it back later always shows `False` and looks like a reset that never fired; and the clone answers **false to all three** of `IsLocal` / `IsMirrorClone` / `IsShadowClone`, so the §Runtimes selection idiom finds nothing. Take the clone from `local.NonLocalClones` (or match `(Non-Local ` in the name). It also lands a frame later, so it is never visible in the call that requests it.

**Diff local-vs-clone params to assert `IsLocal`-branch divergence** (a bit-sync system runs its write side on local, read side on the clone).

**Set `NonLocalSyncInterval` — a field on each clone's `LyumaAv3Runtime`, not the emulator control object — before timing anything against the wire.** The emulator models 8-bit float quantization (~1/127 steps) and a fixed-period sync tick — but **`NonLocalSyncInterval` defaults to 0.2 s, twice VRChat's ~0.1 s**, so set it explicitly or you measure at half rate. That sampler is also **lossless**: it reads the source's current value on tick, with no drop or jitter, so it shows which writes survive *sampling* and never which survive the *network* (`runtime.md` §Parameters owns the paired-write floor that distinction sets).

**The clone's animator runs `CullCompletely`** (local runs AlwaysAnimate — emulator-faithful distance culling), and culling keys off whether the clone's renderers actually *render*: an **unfocused editor renders nothing** (`renderer.isVisible` stays false even with a scene camera aimed at a visible body mesh), so the clone's FX playable silently stops ticking and reads as a graph frozen mid-transition. For graph-logic reads, set the clone's Animator to `AlwaysAnimate` after spawn (a deliberate fidelity trade — you are testing routing, not culling) or keep the editor focused. The clone's FX runs on the playable graph, so its `Animator.runtimeAnimatorController` is null and `GetCurrentAnimatorStateInfo` reads nothing — infer the clone's state from rig pose plus synced params, never from state names.

**Contacts are never simulated against clones — clone contact values are spawn-time fossils, not zeros.** A clone receiver's `paramValue` (and its mirrored animator param) holds whatever the *local* avatar's receiver read at the moment the clone spawned, forever — a clone spawned mid-latch reads latched with no sender anywhere near (the clone's visual offset is render-only and its transforms are true, so a verified overlap changing nothing is the simulation's absence). Every contact assertion runs against the **local** avatar; remote-side contact behavior is in-game-only (or a two-avatar session — below).

**Raycasts do run on the clone, but a *synced* raycast param reads local's replicated value, not the clone's own ray** (measured: the two read opposite on one component); mirror/shadow clones bridge neither.

**The `synced` flag lies both ways** — the baked flag reads synced-false for compressed params that still replicate (VRCFury's Parameter Compressor), and the pre-build asset under-counts (build-time MA/VRCF/prefab merges add synced params) — so judge the synced-bit cost from the post-build `VRCFuryDebugInfo` bit totals (from the bake), never a raw param-asset flag.

**The emulator clamps a driver-written Int to 0–255 only when the param is synced** (`LyumaAv3Runtime.ClampByte` gates on `synced`), Set and Add alike — matching the client (`runtime.md` §Parameters). The two venues split only on a `convertRange` remap landing exactly on a whole number, where av3emu lands one below.

**An induced cull pause is one line**: disable the clone's `Animator` component mid-run and re-enable it — wire params keep updating, evaluation stops, resume sees current values — the stand-in the `vrc-patterns/word-channel` pause fixtures are built on (the real client's pause-time delivery timing stays two-client-only — `vrchat-client.md`).

## Fake another player's contact

A scripted sender fires an `allowOthers`-only receiver solo — know the mechanism: contact self/other is `sender.playerId == receiver.playerId`, and in editor play **every** contact is avatar dynamics (`Usage` defaults to `Avatar` — scripted ones included), so the allow-flag filter always applies. The SDK stamps each avatar's contacts with a per-avatar id at init (`AvatarDynamicsSetup`: the descriptor's hash — junk-looking negative ids are normal), with `EnablePlayerContactPermissions` off too; a sender parented to no avatar keeps the default `-1` and reads as **another player** on the id compare, while the wearer's own senders share the avatar's id and **self-block** on `allowOthers`-only receivers. "Drop the prop on your own head" therefore cannot stand in for another player; a scripted sender (or a second avatar — below) can. And don't assume the descriptor-synthesized `Head`/`Hand` senders as test hardware: synthesis is the emulator control's `DescriptorColliders` setting reading the descriptor's collider slots — absent on a module-scale minimal rig (measured zero) — so count them before use:

```csharp
var go = new UnityEngine.GameObject("Sender"); go.transform.position = head.position;
var s = go.AddComponent<VRC.SDK3.Dynamics.Contact.Components.VRCContactSender>();
s.shapeType = VRC.Dynamics.ContactBase.ShapeType.Sphere; s.radius = 0.05f;
s.rootTransform = go.transform;
s.collisionTags = new System.Collections.Generic.List<string>{ "Hand" };
// next call: read the target receiver's .paramValue / .IsColliding()
```

**Receivers bridge to params only through the runtime's mirror.** That mirror is built from the baked `VRCExpressionParameters` **plus every parameter declared in a playable-layer controller** (the latter enter unsynced, listed `(local)`), and a receiver write to a name in neither is a **silent no-op** — the component's `paramValue` still moves, the mirror never does. So an animator-only param bridges fine (measured: a receiver whose name lives only in the FX controller reads through to the mirror), and MA `NotSynced` dropping a name from the baked asset kills the bridge only when no controller declares it either — the usual real case being a receiver param nothing consumes. MA local-only stays in the asset regardless; receiver type is irrelevant (Constant and Proximity both bridge). And while the contact persists the receiver re-asserts its param, so a manual mirror write silently loses (sibling of the driver-reversion trap) — stimulate the sender, don't puppet the param.

## Two-avatar contact sessions — the faithful self/other venue

The scripted-sender route above unit-tests the allow-flags themselves; take a second avatar when the behavior needs a real other player — descriptor-synthesized senders riding another armature, arbitration across players, a moving-target chase — and flip `EnablePlayerContactPermissions` **on** (the PlayGate one-shot override covers both violated preconditions). Each avatar then runs as its own local player, its contacts re-stamped with its runtime's `contactPlayerId` (small sequential ints replacing the permissions-off descriptor hashes — don't carry ids across the flag flip): cross-avatar contacts are genuinely "other" (avatar B's synthesized Head sender fires A's `allowOthers` cage), self-blocks enforce (A's own head sender reads 0 on A's cage while A's `allowSelf` receiver reads 1 — measured), both animators run un-culled, and scripting avatar B's root makes a moving-target chase test. One trap: head/hand sender synthesis runs twice per avatar and the duplicate carries a junk `playerId` that reads as a *different player*, silently defeating self-blocks — after play starts, destroy every sender whose `playerId` differs from its runtime's `contactPlayerId`. That field is **non-public**: read it with `GetField("contactPlayerId", BindingFlags.NonPublic | BindingFlags.Instance)` and **abort if the read is null** — a defaulted sentinel compares unequal to every sender's id and the loop destroys the legitimate senders too (measured; play-exit to recover). What the route cannot show: anything networked — two locals share no sync channel (remote param routing still needs the clone), and a grab does not transport between them.

## Induce a physbone grab/pose

A live chain re-asserts `_IsGrabbed` every frame, so writing the mirror bool silently reverts (the sibling of the receiver and driver reversion traps; it holds only while the bone GO is inactive, which hides the trap) — induce a real grab instead. Two doors, then recipes and traps, one per paragraph.

**`VRC.Dynamics.PhysBoneManager.Inst.AttemptGrab(grabberId, comp.chainId, bone)` is the reliable door**, measured on every bone index of four chains across three venue shapes — no avatar; an avatar without the emulator; an avatar with it — the returned grab dragging the chain to its target. **`grabberId` must be `0`** (an arbitrary id returns null), `bone` is an **int** chain index, and `comp.chainId` must be read off the **live component in the same call** — a non-public field whose value goes stale silently, since the emulator destroys the manager on `compilationStarted` and re-registration mints new ids. `Inst` itself is null outside play mode, so neither door exists to call there: not the registered-but-unticked shape §Edit-mode VRC constraints describes, and nothing to pump.

**Bracket each attempt: `IsChainGrabbed(chainId)` before, release after.** A repeat `AttemptGrab` on a grabbed chain returns null, so an unbracketed sweep over bone indices reports every index after the first success as null — indistinguishable from a door that never works, the first thing to suspect behind any "every bone index returned null", and why recovery is a `GetGrabs()` → `ReleaseGrab` rather than a retry.

**The spatial door, `AttemptGrab(playerId, grabPosition, grabRadius, sortPosition)`, works at `playerId 0`** but searches the collision structure instead of addressing a chain, so it enforces two requirements the chain-addressed form ignores. The physbone's own **`radius` must be non-zero** — it authors as `0`, and no grabber radius from 0.05 m to 5 m compensates, which alone accounts for a rig that grabs by chain index and never by position. The bone must also be **simulated with a non-zero end radius**, so a chain's unsimulated leaves return null from their own endpoints while every other bone of that chain grabs; vendor rigs ship chains of both kinds, so probe a chain before concluding anything about the door. Reach is sum-of-radii, bone radius + `grabRadius` against the distance: a 0.05 m bone 1.0 m away takes `0.96` and not `0.94`.

**The spatial query is global, so the returned grab may be on a chain other than the one you aimed at** — a wide `grabRadius` prefers whichever candidate `sortPosition` ranks nearest. Release by the returned grab's own `chainId`: releasing by the chain you *intended* leaks the grab, and every later attempt on the real one then reads already-grabbed.

Set `grab.GlobalPosition` in the **same call** for either door (it defaults to origin, else the chain snaps to 0,0,0 — the Vector3 property wraps a `globalPosition` float3 field, and reflection sees only the lowercase field). A call that grabs then throws leaves that origin-grab **live** (chain pinned at 0,0,0), which is one way to arrive at the already-grabbed state above.

Move a grab across calls via `GetGrabs()` (match `chainId`) — the solver drags the chain and `_IsGrabbed` fires. `ReleaseGrab(chainId)` clears it; `ReleaseGrab(grab, true, grabberId)` on an `allowPosing` bone leaves it **held** (read the bone transform; no `_IsPosed` param). Releasing while iterating `GetGrabs()` mutates the collection and **silently skips grabs** — collect to a list first, then release (multiple concurrent grabs under one `grabberId` are fine).

Discover grabbable bones by scanning chains for `allowGrabbing != 0`; offset the target off the bone endpoint or `SolveGrabIK` spams a benign `FromToRotation` assertion.

Two control-experiment traps: a chain that won't drag under a scripted grab is **geometry, not the API** — millimeter-scale bones with default stretch limits barely move (the zipper-tab class); `immobile=1.0` AllMotion itself does **not** pin a grab (it cancels root-induced motion only, `runtime.md` — a grab-prop chain at `immobile 1.0, pull 1` drags to the target exactly).

**Runtime mutation of physbone settings never reaches the native solver** (they bake at chain init), so "change a setting, then grab" silently no-ops — including the `radius` the spatial door needs.

A PB with **no `parameter` declared mints no `_IsGrabbed`/`_Stretch` params at all** — assert the bone transform/chain, not a param.

## Verify mirror-detection

The MirrorReflection clone runs its animator but skips the local avatar's init drivers, so driver-set params (a `MirrorDetection/IsMirror` flag, constant-1 params) stay permanently at their un-driven defaults while local shows the driven value — diff local-vs-mirror.

## What the emulator reproduces — and doesn't

**Reproduced (assert here):** local param drive/read, driven outputs, `IsLocal`-branch divergence, 8-bit sync quantization + the ~0.1 s tick, local contact physics, a scripted "other" sender, filters-check-only-at-acquisition latch persistence (an in-progress contact survives its receiver's allow-flag flipping shut — the held float is the latch working, not a bug), **mirror-clone SMB-asymmetry** (so mirror-detection is testable), a real **local** physbone grab/pose, **`VRCRaycast`** (simulates in play mode against a scene collider, each copy running its own ray), and **OSC parameter traffic** in both directions, including `/input/` commands and the client's rising-edge mute toggle (§OSC).

**Not faithful — needs the shipping client.** Split it by which tier (`verify.md` §The method) actually reaches it before declining the work. **One desktop client** covers OSCQuery announcement and discovery (the emulator implements none), the rewriting of parameter names into addresses, and real frame duration — the editor's frame rate is not a client's, swinging ~12 fps unfocused to 200+ focused, so measure rather than assume. **Two clients** cover network-sync *correctness* (the compressor hides it), remote-side contacts/trackers, real IK smoothing / ~0.5 s body delay, a *networked* grab or **pose late-sync** (a locally-posed bone does not transport to the clone), distance-culling animator pause, controller-input feel, and anything resting on **player colliders** — the editor has none, so a player-mode ray finds nothing, and faking a capsule under the avatar is a **false pass** because the client strips every collider off a real avatar. A player-layer collider does test the *machine* around such a ray — param path, `_Ratio` arithmetic, the latch — but never where a real capsule sits or whose it is. Don't spend a play session chasing the two-client set; the one-client venue is `vrchat-client.md`.

## Cost

Play-mode entry is the bottleneck — the whole non-destructive build runs on every entry (minutes on a heavy avatar) — so **batch every assertion into one play session**; re-enter only to test an asset/controller edit. At module scale the heavy avatar itself is avoidable: an empty GO + descriptor + VRCFury FixWriteDefaults (mode Disabled) + the module under test builds in seconds — default to that rig (plus a camera and a body mesh if a remote clone is involved — §Remote clone) — but **a script-built descriptor needs `baseAnimationLayers`/`specialAnimationLayers` assigned** (the standard entries at `isDefault = true`, no controller), which the inspector does for you and `AddComponent` does not: VRCFury dereferences both arrays for **every** avatar in the scene (`VRCAvatarUtils.GetAllControllers`, which iterates `layers.Length`), so a rig carrying no VRCFury component at all still aborts play entry on an NRE out of it — and **`null` is the trigger, not empty**, so assigning a zero-length array is a valid fix and leaving the field untouched is not. It aborts through a **modal**, so over MCP it presents as a play entry that times out rather than anything in the console. Batch variants as N module instances on the one avatar (satisfies the gate's one-avatar precondition; VRCFury prefixes each FullController's params independently). Within a session compute is cheap, but MCP round-trips and the ~12 fps unfocused throttle gate wall-clock, so time-based settles cost real seconds.
