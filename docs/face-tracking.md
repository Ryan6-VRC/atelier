# Native face tracking

Primary reader: an agent building, verifying or driving the client's native face-tracking system on any avatar. An avatar's own block is its venue record; this file holds what is true of the client and of VRCFaceTracking whatever the avatar. The authoring surface is the descriptor's three lists and the set-weight state behaviour, which `animator-schema.md`'s `faceTrackingSets` kind compiles; VRChat's pages on [face tracking](https://creators.vrchat.com/avatars/face-tracking/), [its OSC input](https://creators.vrchat.com/avatars/face-tracking/osc/) and [the built-in parameters](https://creators.vrchat.com/avatars/animator-parameters/) own the grammar, the key order and the rank thresholds, and are not restated here. Every client claim below was measured on one desktop client over OSC with synthetic blobs; a VR client or a remote viewer may differ where the claim says nothing about them.

## Where time lives

- **A Parameter Behavior has no state.** Its expression grammar carries no smoothing, hysteresis, curve or memory, and a set mapping is a key times a multiplier. The one time constant in the native system is the lerp speed on the set-weight state behaviour, which shapes how a gate fades and nothing else. So per-shape or per-channel smoothing on the avatar means forwarding the value to an animator parameter and smoothing it there, which costs a forwarded slot per channel against the rank ceiling and takes the shape away from its native writer.
- **Source-side smoothing is VRCFaceTracking's and reaches every viewer.** Its mutator pipeline runs before the blob is built (`UnifiedTracking.UpdateDataSync` feeds `BinaryFaceDataSender` the mutated data) and VRChat networks what it receives. The shipped Data Filter is a One-Euro filter whose three knobs are global across every key and gaze axis, so it changes the whole face's feel together; Parameter Adjustment is per-group amplitude, not speed. Fetch `references/VRCFaceTracking` and read `origin/master` for the current set.

## The input as the client takes it

- **A desktop client accepts the blob.** The built-ins go true within a frame or two of the first message and a forwarded value lands one frame later.
- **Send faster than once per 2 s.** At 0.5 Hz every forwarded value drops to zero for one frame every 2 s, visible only on the out-port stream; 1 Hz is clean and 10 to 30 Hz leaves margin.
- **Silence zeroes, it does not freeze or decay.** 2.0 s after the last blob every forwarded value snaps to zero in a single frame, `UserFaceTracking` falls in that frame and `UserEyeTracking` one frame later; gaze returns to the simulated wander over a few frames. A gate on `UserFaceTracking` therefore protects nothing on source loss that the client does not already do.
- **`UserEyeTracking` is not an eye-source flag.** Both built-ins go true for any well-formed blob, an all-zero one included, so a mouth-only source reads as eye tracking. While any blob flows the descriptor's gaze follows the blob's eye keys, zero included, and simulated eye movement stops; a source with no eye module holds the eyes dead straight until the stream ends, and no avatar toggle restores the wander.
- **Forwarded and built-in values are readable over OSC.** They are written by the client's face-tracking system, not by the animator, so like receiver outputs they update on the OSCQuery tree and stream change-only on the out-port (`vrchat-client.md`). Native-written blendshape weights are invisible over OSC: a bake probe verifies the built mappings and that the shapes exist, and whether the client drives them needs an in-world look.
- **One sender at a time.** The client takes the last message, and VRCFaceTracking fills all 102 bytes on every update, so a second sender beside it is overwritten within a frame. A value of your own rides the blob only through a relay that rewrites bytes before forwarding. VRCFaceTracking sends the blob only while the client's OSCQuery says the worn avatar has full face tracking, a check it makes against the client directly, so a UDP relay leaves it working. It sends a full-face-tracking avatar no avatar parameters at all, so any avatar parameter it would drive on a non-native avatar moves on this one only from the menu or a bridge.

## Verifying a block

- **On an AAO build the descriptor's `faceTrackingMeshes` point at the renderer each face mesh merged into (two or more face-tracking meshes are left unmerged), and the sets' and behaviours' shape names are rewritten onto it, or to an empty string where the shape was removed.** A probe that checks the spec's authored names against the merged mesh reports everything missing. Read each enabled key's non-empty name in each built set and each Apply-to-Blendshape target off the built descriptor, check those against the built `faceTrackingMeshes`, and count the empty names separately.
- **An unattended desktop run answers most client questions in minutes**: launch and join per `vrchat-client.md`, stream a blob from a script on `vrc-bridge`'s `OSCManager`, read the forwarded names and built-ins over OSCQuery and the out-port. A remote question needs a second signed-in profile as the viewer (the two-clients-under-`--profile` bullet in `vrchat-client.md`).
