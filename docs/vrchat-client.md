# The live VRChat client as an agent-driven venue

When a claim needs the one-desktop-client tier (`verify.md` §The method — OSCQuery discovery, the client's parameter-name rewriting, real frame duration), the whole session is drivable from this machine over OSC/OSCQuery plus the launch URI — the operator's hands are needed to log an account in for the first time and to answer in-client dialogs, and for nothing else below. All measured on a real client; the drive scripts are a few dozen lines each on `vrc-bridge`'s `OSCManager` (construct extra instances with `advertise=False` — two advertisers collide on the mDNS name). The wire itself — address families, exact typing, latching — is `osc.md`'s.

- **Read the worn avatar over OSCQuery, not the datagram stream.** A single-node or subtree GET serves the live value of every parameter the built avatar declares — unsynced and `scratch:` controller params included, far more than the params asset suggests — which covers receiver outputs and staging wearer-side. Poll at 1 Hz for logging; the datagram stream below is separate plumbing. Match parameters by **suffix**: VRCFury prefixes everything except `globalParams` names with a per-build `VF##_` token.
- **An AAP is served but never updated, so reading one proves nothing.** Measured on a driven rig: four `…/Smoothed` AAPs read exactly `+0.0000` for 22 s while the raw floats feeding them swung to ±0.94 and the avatar visibly moved. The node exists in the tree and answers 200, which is what makes this worth stating — a check written against it passes on a value the animator is not writing. An AAP claim needs a reader that is not OSCQuery, or an in-world observation.
- **A node that carries a value can also have children.** `Left_X` is the raw float *and* the parent of `Left_X/Smoothed`, so a walker that emits only leaves silently drops the half you came for. Read values on container nodes too.
- **Swap avatars with inbound `/avatar/change`** (own uploads/favorites/recents — `osc.md` owns the echo-is-not-outcome trap). The reliable swap tell is state, not names: unsaved params revert to defaults on every swap, so re-arm anything Enable-shaped over OSC afterward, and expect identical builds to share a `VF##_` prefix. A re-upload of the *worn* avatar needs a bounce through another avatar and back to load the new bundle.
- **`vrchat://launch?id=<wrld>:<instance>~region(us)` boots a client into a named instance**, and with one already running boots a *second* rather than switching the first — unattended world switching at the cost of a full relaunch. **Kill the old PID before launching, or give the new client its own `--osc=<in>:<ip>:<out>` ports:** two clients cannot share 9000/9001, and whichever loses the bind serves a dead OSCQuery namespace that never self-heals. Its signature is root `/` answering 200 as a bare leaf while every child 404s, so a subtree GET raises instead of returning empty and a zero-parameter check misses it. The only cure is an in-client OSC toggle — a menu action no drive loop can reach.
- **Verify a join from the client's own log**, never from the launch URI: `%USERPROFILE%\AppData\LocalLow\VRChat\VRChat\output_log_*.txt`, where `[Behaviour] Joining wrld_…` names world and instance and `Successfully joined room` + `Finished entering world.` prove it landed rather than fell back. That file also carries the operator's usr id (`User Authenticated:`) and the client's OSCQuery port (`OSCQuery on <port>`).
- **Default every run to a `~hidden` (Friends+) instance; go public only when the measurement names why** — it needs many players, or a world's populated behaviour. Strangers are uncontrolled variables in avatar count, network load, and what is in frame, and an agent-driven account is on display to them. Non-public types join straight from the URI, no invite flow and no nonce: `~friends(usr_…)`, `~hidden(usr_…)`, `~private(usr_…)~canRequestInvite`.
- **`--no-vr` suppresses the SteamVR launch attempt**, and passes through the registered URI handler (`launch.exe "%1" %*`) so it rides the real relaunch path. Without a headset that attempt raises a dialog an unattended run cannot dismiss.
- **Invoke `launch.exe` directly — never `VRChat.exe` or Steam's `start_protected_game.exe`.** Both silently reuse a prior Steam invocation's cached args and displace the running client via the single-instance slot instead of adding a second one. Working shape: `launch.exe "vrchat://launch?id=<wrld>:<instance>~region(us)" --no-vr "--osc=<in>:<ip>:<out>"`, one call per client.
- **`/input/` moves the player, and every movement address latches.** `Vertical`, `Horizontal`, `MoveForward`, and `LookHorizontal` hold until sent an explicit zero or false; only `Jump` is an edge-triggered impulse that ends on its own. Read the effect off the built-in parameter it surfaces as, never an echo, and hold argument types exact (`osc.md` owns both). Two traps: measure a latch only in **open space**, since geometry that stops the player returns the readout to rest and makes a latch look momentary — the direction that ships a loop walking the avatar away permanently; and pick a readout that **rests at zero**, since `Upright` sits at 1.0 standing and a moved-from-rest test fires on its baseline.
- **The outbound `/avatar/parameters/*` datagram stream does flow** — thousands of datagrams a minute, covering built-ins, `VF##_` sync params, and per-limb tracking state — to the client's **configured out-port** (9001 by default, or whatever `--osc` set) and, in parallel, to **every OSCQuery consumer whose mDNS announcement the client hears**, within ~2 s of the advertisement. On the out-port each changing parameter arrives **once per client frame** (~60 Hz) from a **single UDP source endpoint**; a discovered port gets the stream **doubled** — two sender sockets per advertisement, however announced (`vrc-bridge/docs/design.md` §Inbound delivery semantics owns the census). The trap is the announce interface, not the client: multicast does not cross the loopback interface, so an instrument announcing only there is never discovered and records a false negative while OSC output is healthy — bind the out-port, or announce unpinned, before concluding a stream is absent.
- **Two clients run concurrently under `--profile=<n>`**, each with its own settings, cache, and saved login — two accounts in one instance, mutually visible, and **both agent-drivable in the same window** — leaving one to the operator is a choice, not a constraint. Each needs its own OSC ports, and with two advertisers up mDNS cannot say which client answered: address each by the port from its own log. The pair must meet in `~friends` or `~hidden`, since neither account can invite the other. **Piloting both is unattended; observing is not** — OSC serves each client its own worn avatar and never what it received about the other, so a remote-side claim still needs an in-world readout.
- **World-imposed avatar state is readable**: `/avatar/eyeheight`, `/avatar/eyeheightmin`/`max`, `/avatar/eyeheightscalingallowed` (OSCQuery nodes) plus the `ScaleFactor`/`ScaleModified` params — enough to detect a forced-scale world (`runtime.md` §Scale) from outside the process.
